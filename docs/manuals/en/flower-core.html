Part 1

Getting Started

What problem Flower solves, and one small working example.

01What Flower Is

A tool is best explained by the pain it removes.

The flow already exists — it just isn't written down

Order processing, payment waits, device control, dispatch, multi-turn AI agents: none of these finish in a single method call. They start, wait for something, move on when a signal arrives, and roll back or retry on failure.

That flow usually ends up scattered:

  • a scheduler polling the database
  • an event listener mutating status
  • an enum column plus a large switch that interprets it
  • a background thread and a shared flag

New engineers do not get stuck on the class diagram. They get stuck on one question no diagram answers: when a request arrives, what actually happens, and in what order? That answer lives in no single file.

Write the flow down as one object

Flower's answer is simple. Write the flow as a Flow, list Steps in order, and have each Step return an explicit StepResult.

The whole shape
Flow flow = Flow.builder("order", "ORD-1024")
        .step("accept",  new AcceptOrderStep(orderService))
        .step("payment", new WaitForPaymentStep())
        .step("fulfill", new FulfillOrderStep(warehouse))
        .build();

worker.submit(flow);

“Which step is this on?” becomes a value you can query instead of a guess. “Where does it go next?” becomes a return value instead of a hidden side effect. Waiting is expressed with event subscriptions, signals, and timeouts instead of sleeps and ad-hoc polling.

Good fits

  • Order processing waiting on payment, inventory, or fulfillment signals
  • Game turns waiting for player input and animation completion
  • Logistics and device workflows where work moves through zones
  • AI agent applications: model call → tool wait → validation → approval → action
  • Retryable background coordination that must stay testable
When not to use it

If you have two or three steps and no waiting, an enum and a switch are genuinely enough. If formal state/event/transition modeling is the goal, Spring StateMachine fits better. Flower does not model state; it runs flows.

What Flower is not

Not BPMN, not a Temporal/Camunda replacement, not a YAML workflow engine, not a distributed saga engine, not a human-task platform. It stays inside one JVM on purpose. For distributed transactions or execution replay, use those tools instead.

02The Core Model

Five names. Learn these and the rest follows.

Engine
Top-level container. Owns the Clock, EventBus, listeners, and checkpoint store, and hands them to Workers.
Worker  one thread
Owns the tick loop. Advances each of its Flows once per tick. Default 100 ms.
Flow  FlowId = flowType + flowKey
An ordered list of Steps for one domain instance (one order, one device).
Step  stepId (string)
A small orchestration unit with an onEnter → onTick* → onExit lifecycle.
StepResult
stay · done · repeat · goTo · finish · fail — the only way to move a Flow.
LayerResponsibilityHow you create it
EngineBundles shared services, injects them into Workers, starts and stops everythingEngine.builder()...build()
WorkerSingle-threaded tick loop that advances active Flows in submission orderWorker.builder("name")...build()
FlowTracks “where am I” in its Step listFlow.builder(type, key)...build()
StepStarts work, checks whether it is done, returns a resultclass X extends Step
StepResultExpresses the transition as a valueStepResult.done() etc.
Easy to misread · A Flow is an instance, not a definition

Looks like a Flow is a reusable workflow definition, the way a BPMN diagram is defined once and shared by many requests.

Actually one order = one Flow object. Step instances are created fresh each time too. There is no definition registry and no definition ID. The “definition” is the factory method you wrote.

Two more names and you have everything

stepId is the string label of a Step inside its Flow (used by logs, dumps, checkpoints, and goTo). stepNo is a tiny integer cursor inside one Step. Keeping these two apart is most of what makes Flower code clean. → Section 11

03Terms

Orchestration
Directing several pieces of work in the right order under the right conditions. The real work (charging a card, writing to a database, calling an API) belongs to domain services; a Step only decides when to trigger it and when to move on.
Tick
One pass of a Worker's loop. Each active Flow gets exactly one chance to advance per tick. Default interval 100 ms.
FlowId
flowType + flowKey, e.g. "order" + "ORD-1024". This pair is what prevents duplicate execution.
Terminal state
A state that never advances again: FINISHED, FAILED, CANCELLED, CHECKPOINT_FAILED.
Signal
A named note scoped to one Step. An event handler (on another thread) leaves it; the tick thread reads it. This is the safe way to cross a thread boundary.
Guard
A short function that answers “may this Step run right now?” — pass, hold, redirect, or fail.
Snapshot
An immutable read-only view of a Flow at one moment. Listeners and dumps receive snapshots, never the live Flow.
Checkpoint
The stored position of a durable Flow: which stepId, which stepNo, and whether it had entered.
Idempotent
Doing it twice has the same effect as doing it once. Important during recovery.
SPI
An interface Flower defines but does not implement, so you can plug in your own: EventBus, Clock, FlowCheckpointStore.

04Five-Minute Quickstart

Maven
<dependency>
    <groupId>io.github.flowerjvm</groupId>
    <artifactId>flower-core</artifactId>
    <version>0.1.3</version>
</dependency>
OrderQuickStart.java
import io.github.flowerjvm.flower.core.engine.Engine;
import io.github.flowerjvm.flower.core.event.InMemoryEventBus;
import io.github.flowerjvm.flower.core.flow.Flow;
import io.github.flowerjvm.flower.core.step.Step;
import io.github.flowerjvm.flower.core.step.StepContext;
import io.github.flowerjvm.flower.core.step.StepResult;
import io.github.flowerjvm.flower.core.worker.Worker;

public class OrderQuickStart {

    // 1) A Step: one phase. onTick returns what happens next.
    static final class AcceptStep extends Step {
        @Override protected void onEnter(StepContext ctx) {
            System.out.println("accepting " + ctx.flowId().flowKey());
        }
        @Override protected StepResult onTick(StepContext ctx) {
            return StepResult.done();          // this Step is done; go to the next one
        }
    }

    static final class WaitPaymentStep extends Step {
        @Override protected void onEnter(StepContext ctx) {
            ctx.startTimeout(3_000);
        }
        @Override protected StepResult onTick(StepContext ctx) {
            if (ctx.hasSignal("paid")) return StepResult.done();
            if (ctx.timedOut()) {
                return StepResult.fail(new IllegalStateException("payment step: timed out"));
            }
            return StepResult.stay();          // still waiting; ask me again next tick
        }
    }

    public static void main(String[] args) throws Exception {
        // 2) Worker owns the tick loop
        Worker worker = Worker.builder("orders").intervalMillis(30).build();

        // 3) Engine bundles shared services and injects them
        Engine engine = Engine.builder()
                .eventBus(InMemoryEventBus.create())
                .worker(worker)
                .build();

        // 4) Flow: the plan for THIS order. Build fresh Steps every time.
        Flow flow = Flow.builder("order", "ORD-1024")
                .step("accept",  new AcceptStep())
                .step("payment", new WaitPaymentStep())
                .build();

        engine.start();                        // ticking starts here
        worker.submit(flow);                   // picked up on the next tick

        Thread.sleep(4_000);
        System.out.println("final state = " + flow.state());   // FAILED (no payment signal)
        engine.stop();
    }
}
LineWhat it means
extends StepOnly onTick is required. Override onEnter, onExit, onReset as needed.
onEnter(ctx)Called once when the Step becomes current. Start external work, subscribe, start a timeout here.
onTick(ctx)Called every tick while the Step is current. Must be short and non-blocking. A sleep here stalls every other Flow on that Worker.
StepResult.stay()“Not yet, ask me again next tick.” The standard way to express waiting.
StepResult.done()“This Step is finished, move to the next.” On the last Step the Flow becomes FINISHED.
Engine.builder()Defaults: SystemClock, InMemoryEventBus. At least one Worker required.
worker.submit(flow)Queues the Flow. It activates on the next tick.
In tests

Call engine.attach() instead of start(), and drive ticks yourself with worker.tickOnce(). Combined with ManualClock this makes time fully deterministic. → Section 14

05How a Flow Progresses

Tick by tick, for the example above. This one table is the whole execution model.

WhenFlow stateCurrent StepWhat happens
submitREADY—The Worker accepts the Flow and queues it. No Step has run yet.
tick 1RUNNINGaccept ① registered as active, onFlowSubmitted fires
② onEnter(accept)
③ in the same tick onTick(accept) → done()
④ onExit(accept), move to the next Step
tick 2RUNNINGpaymentonEnter(payment) (timeout starts) → onTick(payment) → no signal → stay()
tick 3…nRUNNINGpaymentOnly onTick repeats. onEnter is not called again.
(external)RUNNINGpaymentA payment event arrives on another thread. The handler calls ctx.signal("paid") and returns immediately.
tick n+1FINISHED—onTick sees the signal → done() → onExit (subscriptions released) → no next Step → onFlowFinished fires
1. Enter and first tick share a tick

onTick runs immediately after onEnter. A Step that finishes on entry passes in one tick.

2. Each transition costs one tick

After done(), the next Step's onEnter runs on the following tick. Ten Steps means at least ten ticks.

3. External threads only leave signals

Handlers set a signal and return. Transitions are always decided by onTick on the tick thread. That is why Step code needs no synchronization.

Easy to misread · “every 100 ms” is really “100 ms after finishing”

Looks like intervalMillis(100) means a tick fires exactly every 100 ms.

Actually it is a fixed delay. If a tick takes 40 ms, the next one starts 100 ms after that — a 140 ms effective period. The upside: ticks never pile up and burst. Heavy ticks slow everything down evenly instead of stampeding.

Choosing an interval

The interval trades latency against CPU. For user-facing flows 20–50 ms; for batch-like flows 200–1000 ms. Far more important than the interval: one slow Step delays every Flow on that Worker.

Builder

FlowId and duplicate submissions

flowType is the kind of flow; flowKey identifies the domain instance. Submitting the same FlowId again is handled by policy:

PolicyBehaviorUse when
REJECT
default		ThrowsDuplicate submission is a bug. Keep this default.
IGNORESilently keeps the existing FlowRetries or restarts where “already running is fine”.
REPLACECancels the existing Flow, installs the new oneA newer request supersedes the previous one.
Multi-tenant: make flowKey globally unique

tenantId is not part of FlowId. If tenants reuse document numbers, encode the tenant in the key itself ("office-a:DOC-1"). Otherwise two tenants' flows collide as duplicates.

Easy to misread · a Flow object cannot be reused

Looks like submit() just queues the object, so you could submit it twice or hand it to another Worker.

Actually submission binds the Flow to that runtime. Two consequences:

① Right after submit(), flow.state() is already READY.
② Submitting the same object twice throws. To run it again, build a new Flow.

This is why Flows are conventionally created by a factory method — you can always build a fresh one.

Recommended: a factory
@Component
public class OrderFlowFactory {

    private final OrderService orderService;
    private final WarehouseService warehouse;

    // constructor injection …

    public Flow create(String orderId) {
        return Flow.builder("order", orderId)
                .step("accept",  new AcceptOrderStep(orderService))
                .step("payment", new WaitPaymentStep(orderService))
                .step("fulfill", new FulfillOrderStep(warehouse))
                .build();
    }
}

Flower has no DI container and never instantiates Steps reflectively. Pass dependencies through constructors. If a Step needs many services, group them into your own Deps object.

07Step Lifecycle

HookRequiredWhen it runs
onEnter(ctx)optionalOnce, when the Step becomes current. Start external work, subscribe, start a timeout.
onTick(ctx)requiredEvery tick while current. Must return a StepResult.
onExit(ctx)optionalWhen leaving (done · goTo · finish · fail · cancel). Not called on repeat.
onReset(ctx)optionalOn repeat(), after the framework has already cleared subscriptions, signals, timeout, and stepNo.
HookDoDon't
onEnter Kick off external work, ctx.subscribe(...), ctx.startTimeout(...) Block waiting for a result. Throwing here fails the Flow without calling onExit.
onTick Check signals, domain state, timeouts; return a result sleep, synchronous HTTP/DB waits, polling loops. One second here delays every Flow on the Worker by one second.
onExit Release resources this Step created, publish a completion event Leave a failure-prone call unguarded — an exception here turns success into failure.
onReset Reset instance fields (retry counters, etc.) Clear subscriptions, signals, timeout, or stepNo — already done for you.
Easy to misread · the first onTick sees nothing yet

Looks like since onEnter started the external call, the first onTick can process its result.

Actually onTick runs in the same tick, microseconds later. The response is almost certainly not back. “Nothing yet → stay()” is the normal first-tick path; assuming otherwise gives you a NullPointerException.

Never share Step instances

A Step is stateful and owned by one Flow. Create new ones for every Flow. Registering production Steps as Spring singletons mixes state across flows.

08StepResult

ResultMeaningSide effects
stay()Keep this Step; call again next tickNothing happens. The standard way to wait.
done()This Step is complete → next declared SteponExit runs, subscriptions released. On the last Step the Flow finishes.
repeat()Restart this Step from the beginningonReset instead of onExit; subscriptions, signals, timeout cleared, stepNo reset. Re-entry is the next tick.
goTo("id")Jump to any stepId, forward or backonExit runs, then the jump. An unknown id fails the Flow.
finish()Skip remaining Steps, succeed nowonExit → FINISHED
fail(cause)Fail the whole FlowonExit → FAILED. cause must not be null.
Easy to misread · when done() and finish() differ

Looks like on the last Step both produce FINISHED, so they are interchangeable.

Actually they only coincide on the last Step, and they differ in meaning and in how they age.

· done() = “this Step is complete” → continues to the next Step. Adding a Step later just works.
· finish() = “the whole Flow is complete” → skips everything after it. Adding a Step later changes nothing; it still stops there.

Use done() for normal completion. Reserve finish() for “the remaining steps are no longer needed”.

Easy to misread · repeat() vs goTo(self)

Looks like both re-run the current Step, so either will do.

Actually they take different hooks.

· repeat() → onReset → (next tick) onEnter. onExit does not run.
· goTo("own id") → onExit → (next tick) onEnter. onReset does not run.

If onExit publishes a completion event, goTo(self) fires it on every loop. Use repeat() for retries.

Easy to misread · goTo does not reset Step fields

Looks like jumping back to an earlier Step re-enters it, so it behaves like a fresh Step.

Actually the Step instance is the same object, and the goTo path does not call onReset (that is repeat() only).

· Reset for you — stepNo, signals, subscriptions, timeout
· Not reset — every instance field you declared

final class ChargeStep extends Step {
    private int attempts;          // NOT reset when goTo returns here

    @Override protected void onEnter(StepContext ctx) {
        attempts = 0;              // reset explicitly on entry
    }
}

This bites hardest in goTo loops such as verify → retry-wait → verify.

An exception in onExit turns success into failure

Even after done(), if onExit throws, the Flow ends as FAILED. Put only failure-tolerant cleanup in onExit; anything that must succeed belongs in onTick before the result is returned.

Keep step ids in constants

A typo in goTo("payment") is only caught at runtime. An enum moves that to compile time.

Wrapping ids
enum OrderStep {
    ACCEPT("accept"), PAYMENT("payment"), FULFILL("fulfill");
    private final String id;
    OrderStep(String id) { this.id = id; }
    String id() { return id; }
}

Flow.builder("order", orderId)
        .step(OrderStep.ACCEPT.id(),  new AcceptOrderStep(orderService))
        .step(OrderStep.PAYMENT.id(), new WaitPaymentStep())
        .build();

return StepResult.goTo(OrderStep.PAYMENT.id());

Flower keeps ids as strings because the same id must be readable in logs, dumps, checkpoints, and admin views.

09Guards

An optional short function that answers “may this Step run right now?”

Attaching a guard
Guard duringBusinessHours = ctx -> {
    LocalTime now = LocalTime.now(ZoneId.of("UTC"));
    if (now.isBefore(LocalTime.of(9, 0)))  return GuardResult.hold();   // too early — wait
    if (now.isAfter(LocalTime.of(18, 0)))  return GuardResult.goTo("defer-to-tomorrow");
    return GuardResult.pass();
};

Flow.builder("settlement", batchId)
        .step("collect", new CollectStep(svc))
        .step("settle",  new SettleStep(svc), duringBusinessHours)
        .step("defer-to-tomorrow", new DeferStep(svc))
        .build();
Guards run on every tick, not just before entry

A Step that has already entered and is waiting must still pass its guard on every tick. The name suggests a one-time entry check; it is not.

ResultIf the Step has not enteredIf it already entered
pass()Enters, then first onTickonTick runs normally
hold()Entry is deferred; onEnter does not runonTick is skipped. Subscriptions and timeout stay alive, onExit does not run — effectively paused
goTo(id)Skipped without enteringonExit runs, then the jump
fail(cause)Flow fails; no onExitonExit runs, then failure
Guard vs stay()

“Not allowed to start yet” is a guard (hold). “Started and waiting” is stay().

Keep guards read-only

No persistence writes, publishing, subscribing, signaling, cancelling, scheduling, or external calls. A guard's own small in-memory counter is fine; business-visible state changes are not. If the check needs phases, waiting, retries, or progress, it is a Step, not a guard.

Interaction with timeouts

While a guard returns hold(), onTick does not run — so timeouts are not observed either. A guarded Step notices its timeout only once the guard passes.

10Waiting: Events, Signals, Timeouts

How to wait without holding a thread.

Subscribe in onEnter, check in onTick
final class WaitForPaymentStep extends Step {

    @Override protected void onEnter(StepContext ctx) {
        ctx.startTimeout(30_000);
        ctx.subscribe(PaymentApproved.class, event -> {  // released automatically
            if (event.orderId().equals(ctx.flowId().flowKey())) {
                ctx.signal("paid", event);               // leave a signal, return immediately
            }
        });
    }

    @Override protected StepResult onTick(StepContext ctx) {
        PaymentApproved approved = ctx.consumeSignal("paid", PaymentApproved.class);
        if (approved != null) {
            orderService.markPaid(approved);             // real work on the tick thread
            return StepResult.done();
        }
        if (ctx.timedOut()) {
            return StepResult.fail(new IllegalStateException("payment step: approval timed out"));
        }
        return StepResult.stay();
    }
}

Subscriptions made through ctx.subscribe(...) are released automatically when the Step exits or resets. You never unsubscribe by hand, and they never leak.

CallBehavior
signal("paid")Marks the signal present, no payload
signal("paid", event)Stores the latest payload. A null payload throws.
hasSignal("paid")Presence check; does not clear
signalPayload("paid", T.class)Reads the payload; the signal remains
consumeSignal("paid", T.class)Reads and clears
clearSignal("paid")Clears only
A signal is not a queue

Three signals with the same name between two ticks leave only the last one. If every event must be processed, put them in your own queue or in domain state and use the signal purely as a “go look” wake-up.

Easy to misread · signals belong to the Step, not the Flow

Looks like a signal left by one Step can be read by the next one.

Actually signals are scoped to a single Step. They disappear when the Step leaves, and the next Step never sees them.

To pass values between Steps use domain state or a run-context object. → Section 11

Subscriptions match the exact runtime type

subscribe(PaymentEvent.class, ...) does not receive PaymentApproved extends PaymentEvent. Prefer concrete, immutable, final event classes.

Timeouts

APIBehavior
startTimeout(ms)Starts a window; calling it again replaces the previous one. Negative values throw. not allowed in durable Flows
timedOut()Whether the window elapsed. Always false if never started.
elapsedMillis()Time since startTimeout; 0 if never started.
Easy to misread · startTimeout does not schedule anything

Looks like after startTimeout(30_000) the framework will do something when 30 seconds pass.

Actually there is no thread, no callback, no scheduled task. timedOut() computes the answer at the moment you call it. If onTick never checks timedOut(), nothing ever happens and the Step stays forever.

Why durable Flows reject startTimeout

Timeout state is not part of a checkpoint. If it were allowed, a restart would silently reset a deadline that had 30 seconds left. Flower chose a loud exception over a quiet bug. In durable flows, store the deadline in domain state and compare it with ctx.clock().currentTimeMillis().

11Sharing Values Between Steps

stepId (string)
  • Position name within the Flow
  • The target of goTo("payment")
  • Appears verbatim in logs, dumps, checkpoints
stepNo (int)
  • A tiny cursor inside one Step
  • “request sent → response checked”
  • Reset to 0 on repeat
Split the Step when…

stepNo starts representing business states like WAITING_PAYMENT or RETRYING.

Sharing values

Use domain state or an explicit run-context object — never stepNo or signals.

Run-context pattern
final class OrderFlowRun {          // a plain object you own
    final String orderId;
    PaymentResult paymentResult;    // shared across accept → payment → fulfill
    OrderFlowRun(String orderId) { this.orderId = orderId; }
}

OrderFlowRun run = new OrderFlowRun(orderId);
Flow flow = Flow.builder("order", orderId)
        .step("accept",  new AcceptOrderStep(run, orderService))
        .step("payment", new WaitPaymentStep(run, paymentService))
        .step("fulfill", new FulfillOrderStep(run, warehouse))
        .build();
A run context is not enough for durable Flows

It lives in memory only and disappears on restart. Anything needed after recovery must be in domain storage. → Section 12

ExecutionContext

A small identity card for one logical execution — not a business context.

Attaching identity
ExecutionContext ctx = ExecutionContext.builder()
        .tenantId("acme")
        .userId("u-42")
        .runId(UUID.randomUUID().toString())
        .traceId(currentTraceId)
        .build();

Flow flow = Flow.builder("order", orderId)
        .executionContext(ctx)
        .step("accept", new AcceptStep())
        .build();

Six optional fields: tenantId · userId · sessionId · runId · traceId · correlationId. They follow the Flow through logs, traces, and checkpoints, and survive durable recovery so the same runId continues.

What not to put here

Roles, policy decisions, approval state, domain objects. Those belong in domain storage. ExecutionContext only stitches one execution together across systems.

12Durable Flows

Checkpoint and resume — not replay. Getting the expectations right matters most.

Stored
  • Which Step it was on
  • Whether it had entered
  • stepNo
  • Execution identity (runId, traceId, …)
  • Definition version
Not stored
  • Step instance fields
  • In-flight events and signals
  • startTimeout state
  • Whether a side effect ran
One rule follows

Everything needed after a restart must live in domain storage. A checkpoint is a bookmark, nothing more.

Making a Flow durable
Flow flow = Flow.builder("order", orderId)
        .durable()                                // ① mark as durable
        .definitionVersion("v3")                  // ② optional
        .durableStep("payment", new WaitPaymentStep(orderService),
                RecoveryPolicy.REENTER_IDEMPOTENT)   // ③ every Step needs a policy
        .durableStep("fulfill", new FulfillOrderStep(warehouse),
                RecoveryPolicy.REENTER_IDEMPOTENT)
        .build();
Recovery policyCalled on recoveryChoose when
REENTER_IDEMPOTENTonEnter runs againEntering is safe to repeat (queries, subscriptions, “already done?” checks).
RESUME_ONLYDurableStep.onResumeFirst entry has side effects (sending a payment request) that recovery must not repeat.
Wiring a store
FlowCheckpointStore store = JdbcFlowCheckpointStore.create(
        dataSource, JdbcCheckpointDialects.postgresql());

Engine engine = Engine.builder()
        .worker(Worker.builder("orders").build())
        .checkpointStore(store)                   // without this, durable submits are rejected
        .build();

flower-persistence-jdbc ships schemas for PostgreSQL, MySQL, Oracle, H2, and SQLite. Tables are never created automatically. Apply the packaged SQL yourself or via Flyway/Liquibase.

Easy to misread · durable misconfiguration fails at two different times

Looks like build() would catch every durable configuration mistake.

Actually different components check different things.

· A Step without a recovery policy → throws at build()
· No durable store wired → build() passes; throws at submit()

“It builds fine but blows up on submit” is expected. Integration tests must submit, not just build.

Idempotency is a precondition

A checkpoint records that a Step was entered, not how far into entry it got. Recovery may therefore run onEnter again and send a payment request twice. Use an idempotency key on external calls, or check domain state for “already done” before acting.

Recovering after a restart

Recovery is explicit; the application calls it.

At startup
FlowFactoryRegistry registry = FlowFactoryRegistry.builder()
        .register("order", id -> orderFlowFactory.create(id.flowKey()))
        .build();

FlowRecoveryService recovery = FlowRecoveryService.create(store, registry);

engine.start();
int restored = recovery.recoverActiveForWorker(engine.worker("orders"));
log.info("recovered {} flows", restored);

Recovery reads the stored position, rebuilds a fresh Flow, and resumes from there. Flower never replays past execution.

Recovering from multiple processes

Flower's duplicate protection is scoped to one Engine in one JVM. Two instances sharing a store can both recover the same Flow simultaneously. Add leader election, row locking, or leases at the application level. Naming Workers per instance and using findActiveByWorker(name) is a practical mitigation.

Two operational notes
  • Checkpoint writes happen synchronously on the tick path. A slow store means slow Flows.
  • If a write fails, the Flow halts as CHECKPOINT_FAILED and onFlowFailed fires. Advancing without a saved position would duplicate side effects after a restart, so Flower stops loudly instead of continuing quietly.

13Observability

Lifecycle listeners

FlowerListener
Map<FlowId, String> lastStep = new ConcurrentHashMap<>();

FlowerListener audit = new FlowerListener() {
    @Override public void onStepEntered(FlowSnapshot f, String stepId) {
        log.info("[{}] → {}", f.flowId(), stepId);
    }
    @Override public void onStepExited(FlowSnapshot f, String stepId) {
        lastStep.put(f.flowId(), stepId);        // remember where we were
    }
    @Override public void onFlowFailed(FlowSnapshot f, Throwable cause) {
        log.error("[{}] failed at {}", f.flowId(), lastStep.remove(f.flowId()), cause);
    }
};

Easy to misread · termination snapshots have no “current step”

Looks like f.currentStepId() inside onFlowFailed would tell you where it failed.

Actually currentStepId() means “the Step currently executing”. A terminated Flow has none, so it is always null there.

Three ways to capture the failure location:
· remember the stepId argument of onStepExited (as above)
· read the STEP_FAILED trace event
· put the Step name in the exception message — simplest and most reliable

return StepResult.fail(new IllegalStateException("payment step: no approval received"));

Note that if onEnter throws, onStepExited never fires either, so the first option will not help. Avoid throwing from onEnter; decide failure in onTick with StepResult.fail(...).

Listeners run on the tick thread

A database query or HTTP call inside a listener slows every Flow on that Worker. Copy what you need, enqueue it, and return.

Trace stream

Registering a FlowerTraceListener turns on a structured execution stream. If none is registered, no trace objects are created at all — the cost is zero.

Receiving traces
FlowerTraceListener trace = event -> log.info("{} seq={} flow={} attrs={}",
        event.type(), event.sequence(), event.flowId(), event.attributes());

Engine engine = Engine.builder().worker(worker).listener(trace).build();

Standard types include FLOW_STARTED, STEP_STARTED, STEP_COMPLETED, STEP_FAILED, CHECKPOINT_SAVED, and FLOW_COMPLETED, with traceId, flowRunId, stepRunId, and sequence numbers. flower-observability provides logging, Micrometer, and OpenTelemetry listeners.

No business payloads

Trace events carry orchestration metadata only. Order contents, model prompts, and secrets are never included. Add and mask those yourself if you need them.

14Testing

Flower's most practical advantage: no threads, no waiting, no flaky tests.

Two rules: call engine.attach() instead of start(), and advance time yourself with worker.tickOnce().

Basic pattern
@Test
void completesWhenPaymentSignalArrives() {
    ManualClock clock = new ManualClock();
    InMemoryEventBus bus = InMemoryEventBus.create();
    Worker worker = Worker.builder("test").build();

    Engine engine = Engine.builder()
            .clock(clock).eventBus(bus).worker(worker).build();
    engine.attach();                    // not start() — no scheduler

    Flow flow = Flow.builder("order", "ORD-1")
            .step("accept",  new AcceptStep())
            .step("payment", new WaitPaymentStep())
            .build();

    worker.submit(flow);
    worker.tickOnce();                  // activate + accept enters and completes
    worker.tickOnce();                  // payment enters, first onTick

    assertThat(flow.currentStepId()).isEqualTo("payment");

    bus.publish(new PaymentApproved("ORD-1"));   // synchronous dispatch
    worker.tickOnce();

    assertThat(flow.state()).isEqualTo(FlowState.FINISHED);
}

@Test
void failsWhenTheTimeoutElapses() {
    // … same setup …
    worker.tickOnce();
    worker.tickOnce();                  // payment enters, startTimeout(30_000)

    clock.advance(30_000);              // jump forward instantly
    worker.tickOnce();

    assertThat(flow.state()).isEqualTo(FlowState.FAILED);
}

Activate a submitted Flow and enter the first Step1

While a guard returns hold()0 progress
Checklist
  • Never call engine.start() in a test — tickOnce() will throw if you do.
  • Drive all time with ManualClock.advance(). No Thread.sleep.
  • Publish events directly from the test thread; InMemoryEventBus dispatches synchronously.
  • Call tickOnce() only from the test or host control thread — never from a Step, Guard, or listener.
  • See flower-testkit for higher-level helpers.

15Rules and Anti-Patterns

✕ Don't✓ Do
Synchronous HTTP, sleep, or DB polling in onTickStart asynchronously in onEnter; onTick only checks signals, domain state, and timeouts
Mutating Flow or Step state from an event handlerHandlers call ctx.signal(...) only; onTick decides transitions
Encoding business states like WAITING or RETRYING in stepNoSplit into named Steps with their own stepId
Sharing Step instances as singleton beansnew per Flow; dependencies through the constructor
Hiding cross-Step values in signals or stepNoDomain state or an explicit run-context object
Step-id string literals scattered through the codeWrap them in an enum or constants
Mutating state or calling out from a GuardGuards decide only; side effects belong in Steps
Cleanup only in onExit, so repeat skips itSubscriptions, signals, and timeouts are auto-cleaned; put the rest in onReset too
Deciding completion from signals alone in a durable FlowAlso check domain state that survives a restart
Database writes or HTTP calls inside listenersEnqueue and return
Putting the whole business process inside one StepKeep Steps thin; delegate to services
Event hierarchies with supertype subscriptionsSubscribe to the exact type — matching is exact
One Worker per feature, screen, or endpointWorkers are execution lanes. Split only for different blocking risk, priority, isolation, or backpressure
Letting @Scheduled or cron own workflow progressionProgression belongs to Flow/Step code. Model periodic checks as long-lived Flows
Calling submit() before the transaction commitsSubmit after commit — otherwise a tick reads uncommitted data
Keeping a durable Flow's completion state only in a Future or Step fieldIt vanishes on restart. Persist the operation id, status, and result
Calling tickOnce() from a Step, Guard, or listenerRe-entry throws. Drive ticks from the test or host control thread
One-line principle

“A Step starts work, checks state, and returns an explicit result.” Code that does not fit that sentence usually belongs in a service. To enforce this at build time, see flower-check.

16Common Mistakes

I submitted a Flow and nothing happens
Check that engine.start() was called. With only attach() no ticks run, so you must call worker.tickOnce() yourself.
tickOnce() throws
The Worker is already scheduler-driven via start(). In tests stop at engine.attach(). It also throws on re-entry from a Step or listener.
I published an event but the Step never saw it
① exact runtime type? (supertype subscriptions do not work) ② is that Step still the current Step? ③ same EventBus instance?
onExit never runs
You are on the repeat() path (onReset runs instead), onEnter threw, or a durable Flow was suspended at shutdown.
I returned done() but the Flow failed
Most likely onExit threw. That is the only path that turns success into failure.
Submitting a durable Flow throws
Either no checkpoint store is wired, or a Step lacks a recovery policy. The latter throws at build(), the former at submit().
startTimeout throws in a durable Flow
Intentional — timeout state is not checkpointed. Store the deadline in domain state and compare against ctx.clock().currentTimeMillis().
The same order runs twice
Within one Engine the same FlowId is blocked. If two processes each recovered it, you need application-level locking or leader election.
My Flow is slow
Minimum duration is step count × tick interval (10 Steps at 100 ms = 1 second). Shorten the interval or merge Steps — but first check whether a slow Step is sharing the Worker.
start() fails after stop()
Engines and Workers are not reusable. Create new ones. For a temporary halt use pause() / resume().

Ten things to remember

  1. Each Flow advances once per tick.
  2. onEnter and the first onTick share one tick.
  3. Every Step transition costs one tick.
  4. onTick never blocks — every Flow on the Worker stops with it.
  5. External threads leave signals only; the tick thread changes state.
  6. Event subscriptions match the exact runtime type.
  7. repeat() calls onReset, not onExit.
  8. An exception in onExit turns success into failure.
  9. Durable stores the position only. Everything else goes in domain storage.
  10. Guards run every tick, entered or not.
