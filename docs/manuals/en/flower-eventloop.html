Flower EventLoop

Instead of waking a Flow periodically to ask whether it is ready, a Step declares what should wake it and sleeps. Built for flows that wait on things with unpredictable timing: LLM responses, tool calls, human approvals.

Part 1

Getting Started

Why a second runtime exists, and one small example.

01Why a Second Runtime

In one line: it replaces polling with subscription.

Where ticking runs out

A Core Worker wakes every live Flow every 100 ms and calls onTick(). The Step answers “not yet” (stay()) and goes back to sleep. Simple and easy to test.

Now consider:

  • 1,000 Flows waiting up to 30 seconds for an LLM response
  • 200 Flows waiting three days for a human approval

That is 1,200 onTick() calls every 100 ms, nearly all of them answering “not yet”. And when a response finally arrives, it waits up to another 100 ms to be noticed.

Declare what should wake you

An event step never says “ask me later”. It says “wake me when one of these happens” and sleeps completely.

The core idea in one statement
return EventStepResult.await(
        AwaitCondition.event(LlmResponded.class),   // wake me on this event
        AwaitCondition.deadlineIn(30_000))          // or after 30 seconds
        .thenPublish(new LlmRequested("hello"));    // then send this request

A waiting Flow consumes no CPU at all and wakes the instant its event arrives, with no polling latency. Whether there are 1,000 or 100,000 waiting Flows barely changes the cost.

SituationWhy the event loop fits
LLM / agent turnsResponse timing is unpredictable; you want zero added latency plus a timeout.
Tool-call waitsResponses must be matched by a correlation key such as callId.
Human approvalsMay take days. Polling for days is pure waste.
Webhooks and callbacksOne-shot responses at an unknown time.
Many idle FlowsWaiting cost does not scale with the number of Flows.
When Core is the better choice
  • Work that must be checked periodically — “did the database change?” has no event to wait for. Expressing that here means awkwardly re-arming deadlines.
  • Flows without real waiting — no waiting, no benefit.
  • Stability-critical code — Core's API is settled; this one is MVP.

Easy to misread · an EventWorker cannot go into an Engine

Looks like both are Flower, so Engine.builder().worker(eventWorker) should manage them together.

Actually Engine.worker(...) accepts only Core's Worker. Give the Clock, EventBus, listeners, and store directly to the EventWorker builder, and call start()/stop() yourself.

You can absolutely run both runtimes in one application — share the same EventBus instance and they can exchange events.

03Quickstart

Maven
<dependency>
    <groupId>io.github.flowerjvm</groupId>
    <artifactId>flower-eventloop</artifactId>
    <version>0.1.3</version>
</dependency>
LlmQuickStart.java
import io.github.flowerjvm.flower.core.event.InMemoryEventBus;
import io.github.flowerjvm.flower.core.time.SystemClock;
import io.github.flowerjvm.flower.eventloop.flow.EventFlow;
import io.github.flowerjvm.flower.eventloop.step.*;
import io.github.flowerjvm.flower.eventloop.worker.EventWorker;

public class LlmQuickStart {

    // Events — immutable classes (matching is by exact type)
    static final class LlmRequested { final String prompt;
        LlmRequested(String p) { this.prompt = p; } }
    static final class LlmResponded { final String text;
        LlmResponded(String t) { this.text = t; } }

    static final class AskStep extends EventStep {
        @Override protected EventStepResult onEnter(EventStepContext ctx) {
            return EventStepResult
                    .await(AwaitCondition.event(LlmResponded.class),   // response, or
                           AwaitCondition.deadlineIn(30_000))          // 30 seconds
                    .thenPublish(new LlmRequested("hi"));              // published AFTER subscribing
        }

        @Override protected EventStepResult onEvent(EventStepContext ctx, Object event) {
            LlmResponded res = (LlmResponded) event;
            System.out.println("response: " + res.text);
            return EventStepResult.next();
        }

        @Override protected EventStepResult onTimeout(EventStepContext ctx) {
            return EventStepResult.goTo("fallback");
        }
    }

    static final class DoneStep extends EventStep {
        private final String label;
        DoneStep(String label) { this.label = label; }
        @Override protected EventStepResult onEnter(EventStepContext ctx) {
            System.out.println("done: " + label);
            return EventStepResult.finish();
        }
    }

    public static void main(String[] args) throws Exception {
        InMemoryEventBus bus = InMemoryEventBus.create();

        // No Engine. Clock and EventBus are given directly; both required.
        EventWorker worker = EventWorker.builder("llm")
                .clock(SystemClock.INSTANCE)
                .eventBus(bus)
                .build();

        // The outside world that answers the request (stubbed here)
        bus.subscribe(LlmRequested.class, req -> bus.publish(new LlmResponded("hello back")));

        EventFlow flow = EventFlow.builder("llm-call", "req-1")
                .step("ask",      new AskStep())
                .step("complete", new DoneStep("completed"))
                .step("fallback", new DoneStep("timed out"))
                .build();

        worker.start();            // one daemon thread
        worker.submit(flow);

        Thread.sleep(500);
        worker.stop();
    }
}
HereIn Core

.clock(...).eventBus(...)		The Engine owned these and injected them. Now the worker takes them directly (both required).

Easy to misread · a waiting Flow is not “running”

Looks like while waiting for a response, the worker is somehow tending that Flow.

Actually the worker has completely forgotten it. All that remains is one event subscription and one deadline entry. Until one of them fires, not a single line of code runs for that Flow.

That is why 100,000 waiting Flows cost almost nothing — and also why nothing will ever wake a Flow that nobody wakes. An await without a deadline can hang forever.

Part 2

Writing Flows

04EventStep Lifecycle

Five hooks. Two of them fail by default, which you must know.

HookRequiredReturnsWhen
onEnter(ctx)yesEventStepResultOnce, when the Step becomes current. Usually returns await(...).
onEvent(ctx, event)optionalresult or nullAn awaited event arrived. Default returns null (ignore, keep waiting).
onTimeout(ctx)optionalresult or nullA deadline elapsed. default fails the Flow
onRecover(ctx, recovery)durable: yesEventStepResultRestored from a checkpoint, instead of onEnter. default fails
onExit(ctx)optionalvoidLeaving the Step.
Easy to misread · the same null means three different things

Looks like returning nothing is handled the same way everywhere.

Actually it splits three ways:

· onEnter returns null → the Flow fails
· onEvent returns null → ignore this event, keep the current waits (a normal, supported pattern)
· onTimeout returns null → drop the deadline only, keep waiting on events

Returning null from onEvent is the idiomatic way to say “not the event I wanted” when you await several types at once.

Two hooks fail by default

onTimeout and onRecover fail the Flow unless you override them. This is deliberate: it refuses to let a mistake pass silently. If you set a deadlineIn(...), implement onTimeout. If you call durable(), implement onRecover.

05EventStepResult

ResultMeaningSide effects
await(c1, c2, ...)Stay on this Step until one condition firesClears all existing waits, registers the new ones, then runs effects. Zero conditions throws.
next()Step complete → next SteponExit, waits cleared. Last Step finishes the Flow. (Core's done())
goTo("id")Jump to any stepIdonExit, waits cleared. Unknown id fails.
finish()Skip the rest, succeedonExit → FINISHED
fail(cause)Fail the FlowonExit → FAILED
Easy to misread · await replaces, it does not add

Looks like returning await(event(B.class)) from onEvent adds B to the existing wait on A.

Actually every existing wait is cleared and only B remains — including the deadline.

To wait on both, declare everything again:

// ✕ A and the deadline are gone
return EventStepResult.await(AwaitCondition.event(B.class));

// ✓ re-declare everything you still want
return EventStepResult.await(
        AwaitCondition.event(A.class),
        AwaitCondition.event(B.class),
        AwaitCondition.deadlineIn(remainingMillis));   // compute the remainder yourself

Deadlines restart from the moment of registration. Passing deadlineIn(30_000) every time extends the deadline by 30 seconds on each event. For an overall deadline, compute the remaining time from ctx.now().

06AwaitCondition

ConstructorWakes onNotes
event(Foo.class)A published FooExact runtime type only. Subclasses do not match.
event(Foo.class, predicate)Type match + predicateFilters like “only my order”. not allowed in durable Flows
signal("tool-call", callId)A matching named signalName and key both required. Safe for durable Flows.
deadlineIn(30_000)30 seconds after registrationNegative throws; 0 expires immediately.
Easy to misread · multiple deadlines collapse into one

Looks like await(event(A), deadlineIn(5000), event(B), deadlineIn(30000)) gives each condition its own timeout.

Actually only the earliest deadline survives. Here that is 5 seconds, after which onTimeout fires once — and you cannot tell which condition timed out.

For per-phase deadlines, split the Step, or wake on the short deadline and re-declare the remaining time from onTimeout.

Easy to misread · a timeout does not cancel the event waits

Looks like when the deadline fires, all waits for that Step are over.

Actually if onTimeout returns null, only the deadline is removed; event and signal waits stay armed. That is the supported way to say “late, but still waiting”.

@Override protected EventStepResult onTimeout(EventStepContext ctx) {
    alertService.warn("slow response: " + ctx.flowId());
    return null;      // deadline gone, still waiting for the response
}

Remember the flip side: the default implementation fails the Flow, so an unimplemented onTimeout kills it.

When a wake-up is silently ignored

If you published an event and nothing happened, check:

  • the runtime type does not match exactly (supertype waits never fire)
  • the signal name or key differs
  • the Step already replaced its waits or moved on
  • it is not the same EventBus instance

These are dropped silently — nothing is logged.

07Effects and Ordering

Why thenPublish exists, and what it does not guarantee.

Why publishing inside onEnter is unsafe

InMemoryEventBus is synchronous: publishing runs the handlers right there.

✕ can lose the response
@Override protected EventStepResult onEnter(EventStepContext ctx) {
    ctx.eventBus().publish(new LlmRequested("hi"));    // ① what if the response fires here?
    return EventStepResult.await(                       // ② subscription registered after this returns
            AwaitCondition.event(LlmResponded.class));  // → response missed forever
}

If the responder answers immediately (a cache hit, a synchronous stub), no subscription exists yet. The response vanishes and the Flow waits until its deadline. This is hard to reproduce and tends to surface only in production.

✓ effects invert the order
return EventStepResult
        .await(AwaitCondition.event(LlmResponded.class))   // ① subscribe first
        .thenPublish(new LlmRequested("hi"));              // ② then publish — safe
MethodRuns onUse for
thenPublish(event)loop threadPublishing an event. The common case.
thenRun(effect)loop threadImmediate work: counters, logs.
thenRunAsync(effect)async executorPotentially blocking work: HTTP, DB, LLM calls.

Handling blocking work

Async executor
ExecutorService pool = Executors.newFixedThreadPool(8);

EventWorker worker = EventWorker.builder("agent")
        .clock(SystemClock.INSTANCE)
        .eventBus(bus)
        .asyncExecutor(pool)          // without this, runAsync throws
        .build();

// inside a Step
@Override protected EventStepResult onEnter(EventStepContext ctx) {
    final String callId = ctx.flowId().flowKey();     // ① capture immutable values first
    return EventStepResult
            .await(AwaitCondition.signal("llm", callId),
                   AwaitCondition.signal("llm-error", callId),
                   AwaitCondition.deadlineIn(60_000))
            .thenRunAsync(c -> {                       // ② another thread from here
                try {
                    c.signal("llm", callId, llmClient.complete(prompt));
                } catch (Exception e) {
                    c.signal("llm-error", callId, e.getMessage());   // ③ report failures too
                }
            });
}
Exceptions in async work do not fail the Flow

If a runAsync task throws, the Flow never learns about it and keeps waiting until its deadline. Always catch and report failures as signals, and declare those signals in the await.

Do not read flow state from async work

Async tasks run outside the loop thread, and by then the Flow may have moved on. Never read mutable state such as ctx.currentStepId(); capture what you need in local variables before returning the result.

Effects are not exactly-once

In a durable Flow, a crash at the wrong moment can leave a saved wait whose request was never sent, or cause the same effect to run twice.

For important external work (payments, emails, tool execution), pair this with a durable outbox or a stable idempotency key. The framework cannot do it for you.

08EventSignal

One class, but central to durable flows.

An EventSignal carries a (name, key, optional payload). Publish with ctx.signal("tool-call", callId, result); wait with AwaitCondition.signal("tool-call", callId).

Why it exists

There are two ways to express “only the response for my request”: a predicate (a lambda) or a data-shaped key. Lambdas cannot be checkpointed, so Flower provides a storable correlation mechanism instead. In durable flows, use signals.

APINotes
EventSignal.of(name, key)No payload
EventSignal.of(name, key, payload)A null payload throws
ctx.signal(name, key[, payload])Shortcut from inside a Step
worker.signal(name, key[, payload])From outside (a webhook controller, for example)
sig.payload(Type.class)Typed accessor; null when absent
Easy to misread · only the name is shared with Core's “signal”

Looks like since Core had ctx.signal("paid"), this is the same Step-local note.

Actually they are entirely different things.

· Core signal: a note inside one Step. Never leaves it; disappears when the Step ends.
· EventLoop signal: an event published on the EventBus. Everyone sharing that bus can see it, and it reaches a Step only if that Step is explicitly awaiting it.

So here ctx.signal(...) does not mean “leave a note” — it means “broadcast”. With no matching await, it simply disappears.

09Durable Flows

Core's durable model plus “what it was waiting for”.

Stored
  • Current Step and entry state
  • The list of pending waits (event type names, signal name/key, deadline)
  • Execution identity (runId, traceId, …)
Not stored
  • Step instance fields
  • Predicate lambdas
  • In-flight event objects
  • Whether an effect ran
Deadlines are absolute

Stored as a point in time, not “30 seconds from now”, so restarts never push the deadline back.

ConstraintFails atWhat to do
No predicate-based event waitswhen the wait is armed (runtime)Use signal(name, key), or await the plain type and filter in onEvent returning null
onRecover must be implementedduring recovery (runtime)The default fails. Override it in every durable Step.
A durable store is requiredsubmit()Build succeeds; only submission catches this.
Easy to misread · the predicate restriction fires when that Step runs

Looks like using a predicate in a durable Flow would be rejected at build time.

Actually AwaitCondition.event(Foo.class, predicate) constructs fine. It fails when the worker tries to write that wait to a checkpoint — that is, when the Step actually executes.

If only the fifth Step uses a predicate, the first four work and the Flow fails in production, at that point. When converting to durable, audit every await in the Flow.

// ✕ fails in a durable Flow
AwaitCondition.event(ToolDone.class, e -> e.callId().equals(myCallId))

// ✓ correlation as data — storable
AwaitCondition.signal("tool-done", myCallId)

// ✓ or await the type and filter in onEvent
AwaitCondition.event(ToolDone.class)
// onEvent: if (!e.callId().equals(myCallId)) return null;
Writing onRecover
@Override
protected EventStepResult onRecover(EventStepContext ctx, EventRecoveryContext recovery) {
    List<AwaitCondition> conditions = new ArrayList<>();

    for (EventAwaitCheckpoint saved : recovery.awaits()) {
        switch (saved.type()) {
            case SIGNAL:
                conditions.add(AwaitCondition.signal(saved.signalName(), saved.signalKey()));
                break;
            case DEADLINE:
                // absolute time → time remaining (0 if already past)
                conditions.add(AwaitCondition.deadlineIn(recovery.millisUntil(saved, ctx.now())));
                break;
            case EVENT:
                conditions.add(AwaitCondition.event(ToolDone.class));
                break;
        }
    }
    // Do NOT re-send the request here — it already went out.
    return EventStepResult.await(conditions.toArray(new AwaitCondition[0]));
}
Recovering at startup
EventFlowFactoryRegistry registry = EventFlowFactoryRegistry.builder()
        .register("llm-call", id -> buildFlow(id.flowKey()))
        .build();

EventFlowRecoveryService recovery =
        EventFlowRecoveryService.create(store, registry);

worker.start();
int restored = recovery.recoverActiveForWorker(worker);
Easy to misread · recovery re-arms waits; it does not resume execution

Looks like after recovery the Flow simply carries on where it left off.

Actually recovery restores only the fact that “this Step was waiting for these things”. The waits are re-armed by the await(...) your onRecover returns. Without the Step's cooperation, recovery is incomplete.

· No onRecover → fails immediately on recovery
· Declaring fewer waits → some stored conditions never come back
· Calling onEnter from onRecover → the request goes out twice

The inconvenience is deliberate: only the domain knows what should and should not be repeated.

Recovering from multiple processes

Preventing duplicate execution is entirely the application's responsibility. Use leader election, row locking, or leases. Naming workers per instance and using findActiveByWorker(name) is the most practical mitigation.

10Observability

The listener interface is identical to Core's, plus two extra trace events.

Registering a listener
EventWorker worker = EventWorker.builder("agent")
        .clock(SystemClock.INSTANCE)
        .eventBus(bus)
        .listener(myListener)        // on the worker, not an Engine
        .build();

onFlowSubmitted, onStepEntered, onStepExited, onFlowFinished, onFlowFailed, onFlowCancelled — the same callbacks. You can register one listener object with both a Core Worker and an EventWorker.

Trace eventContents
FLOW_WAITINGEmitted right after waits are armed. Carries what it is waiting for.
FLOW_RESUMEDEmitted on wake-up. Carries why: EVENT, SIGNAL, TIMEOUT, or RECOVERY.
Measure real wait time directly

The gap between a matching FLOW_WAITING and FLOW_RESUMED is the wait duration, and the resume reason tells you how it ended. You get LLM latency distributions and approval turnaround times for free.

Easy to misread · stateOf() returning null is not a failure

Looks like a null from worker.stateOf(id) means something went wrong.

Actually it means “not in the active list” — most often because it completed normally and was removed. A Flow never submitted is also null.

For the final outcome, read flow.state() on the Flow object or use a termination listener.

11Testing

As deterministic as Core. drain() takes the place of tickOnce().

Basic pattern
@Test
void completesWhenTheResponseArrives() {
    ManualClock clock = new ManualClock();
    InMemoryEventBus bus = InMemoryEventBus.create();
    EventWorker worker = EventWorker.builder("llm")
            .clock(clock).eventBus(bus).build();     // never call start()

    EventFlow flow = buildFlow();
    worker.submit(flow);
    worker.drain();                                   // entry + wait registration

    assertThat(flow.state()).isEqualTo(FlowState.RUNNING);   // waiting

    bus.publish(new LlmResponded("hi"));
    worker.drain();

    assertThat(flow.state()).isEqualTo(FlowState.FINISHED);
}

@Test
void routesToFallbackWhenTheDeadlineElapses() {
    // … same setup …
    worker.submit(flow);
    worker.drain();

    clock.advance(30_000);                            // jump forward
    worker.drain();                                   // process expired deadlines

    assertThat(log).containsExactly("fallback");
}
Easy to misread · drain() and start() cannot be mixed

Looks like you could start() the worker and still call drain() to push it along in a test.

Actually drain() throws immediately in background mode. In tests, never call start() — use ManualClock plus drain().

Checklist
  • drain() runs until nothing more can progress, so ten consecutive non-waiting Steps pass in one call.
  • Drive all time with ManualClock.advance().
  • Publish events from the test thread; dispatch is synchronous.
  • For Steps using runAsync, pass a same-thread executor (Runnable::run) to keep tests deterministic.

Using It Well

12Rules and Anti-Patterns

✕ Don't✓ Do
Publish directly inside onEnterUse .thenPublish(...) so subscription happens first
await without a deadlineAttach deadlineIn(...) to every await — the only thing that surfaces a stuck Flow
Setting deadlineIn without implementing onTimeoutRemember the default fails; always override it
HTTP, DB, or LLM calls on the loop threadthenRunAsync with an executor; report completion as a signal
Letting async work throwCatch it and signal the failure, and await that signal too
Reading ctx.currentStepId() from async workCapture the values you need in locals first
Re-declaring only some conditions in onEventRe-declare everything you still want (await replaces)
Predicate waits in durable Flowssignal(name, key), or filter in onEvent and return null
durable() without onRecoverSpell out what to re-arm and what not to repeat
Calling onEnter from onRecoverRe-arm waits only; never resend one-shot requests
Event hierarchies with supertype waitsExact types — matching is exact
Relying on effects for critical external workAdd an outbox or idempotency key — effects are not exactly-once
The typical failure here is not an error — it is silence

A deadline-less await, an async task that died, a wake-up that was silently dropped: each produces a Flow that stops with nothing in the logs.

There is one defense: put a deadline on every await. Then at least onTimeout fires and the problem becomes visible.

One-line principle

“A Step declares what should wake it, then decides when it wakes.” Anything you did not declare will never arrive.

13Mistakes · Cheat Sheet

I submitted a Flow and nothing happens
Check that start() was called. In tests, call drain().
I published an event but nothing woke up
① exact runtime type? ② same EventBus? ③ is that Step still awaiting that condition? ④ for signals, do both name and key match?
The Flow is stuck and there are no logs
A deadline-less await, an async task that threw, or a silently dropped wake-up.
drain() throws
The worker is already in background mode from start().
Going durable broke one specific step
That step's await most likely uses a predicate.
Recovery fails immediately
onRecover is not implemented; the default fails.
ClassCastException in onEvent
When awaiting several types you cannot know which arrives. Check with instanceof and return null if it is not yours.
Can I run it alongside a Core Worker?
Yes. It cannot join an Engine, but sharing one EventBus lets both runtimes talk.
Can a worker be restarted?
No. After stop(), build a new one.

Eight things to remember

  1. A waiting Flow runs no code at all. Nothing wakes it unless something declared wakes it.
  2. await replaces the current waits; it does not add to them.
  3. Multiple deadlines collapse into the earliest one.
  4. onTimeout and onRecover fail by default.
  5. null means something different in each hook.
  6. Send requests via thenPublish — subscribe first, publish second.
  7. Async exceptions never reach the Flow. Signal failures explicitly.
  8. Durable means no predicates and a required onRecover.
