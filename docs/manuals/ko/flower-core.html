01Flower란 무엇인가

먼저 “왜 필요한가”부터. 도구의 정체는 그 도구가 없앤 고통에서 가장 잘 드러납니다.

흐름은 이미 있는데, 어디에도 적혀 있지 않습니다

주문 처리, 결제 대기, 장비 제어, 배차, AI 에이전트의 여러 턴 — 이런 일은 한 번의 메서드 호출로 끝나지 않습니다. 시작하고, 무언가를 기다리고, 신호가 오면 다음 단계로 넘어가고, 실패하면 되돌리거나 재시도합니다.

보통 이 “흐름”은 코드 여기저기로 흩어집니다.

  • 주기적으로 DB를 뒤지는 스케줄러 하나
  • 메시지가 오면 상태를 바꾸는 이벤트 리스너 하나
  • “지금 어디까지 왔는지”를 담은 enum 컬럼과 그걸 해석하는 거대한 switch
  • 중간에 끼어든 백그라운드 스레드와 공유 플래그

새로 온 개발자가 막히는 지점은 클래스 다이어그램이 아니라 “요청이 들어오면 실제로 무슨 일이 어떤 순서로 일어나는가”입니다. 그 답은 어느 한 파일에도 없습니다.

흐름을 하나의 객체로 적어 둡니다

Flower의 답은 단순합니다. 흐름을 Flow로 적고, 그 안에 Step을 순서대로 나열합니다. 각 Step은 “다음에 뭘 할지”를 StepResult로 명시적으로 반환합니다.

한눈에 보는 형태
Flow flow = Flow.builder("order", "ORD-1024")
        .step("accept",  new AcceptOrderStep(orderService))
        .step("payment", new WaitForPaymentStep())
        .step("fulfill", new FulfillOrderStep(warehouse))
        .build();

worker.submit(flow);

“지금 어느 단계인가”는 추측이 아니라 조회할 수 있는 값이 되고, “다음에 어디로 가는가”는 숨은 부수효과가 아니라 반환값이 됩니다. 기다림은 Thread.sleep이나 폴링 루프가 아니라 이벤트 구독 · 시그널 · 타임아웃으로 표현됩니다.

어떤 일에 맞나

  • 결제·재고·배송 신호를 기다리는 주문 처리
  • 플레이어 입력과 애니메이션 완료를 기다리는 게임 턴
  • 구역을 이동하며 단계가 바뀌는 물류·장비 워크플로
  • 모델 호출 → 도구 대기 → 검증 → 승인 → 실행으로 이어지는 AI 에이전트 애플리케이션
  • 결정적으로 테스트해야 하는 재시도 가능한 백그라운드 조정 로직
굳이 안 써도 되는 경우

단계가 2~3개고 기다림이 없다면 enum + switch로 충분합니다. 형식적인 상태·이벤트·전이 모델링 자체가 목적이면 Spring StateMachine이 더 맞습니다. Flower는 “상태를 모델링”하는 도구가 아니라 “흐름을 실행”하는 도구입니다.

Flower가 아닌 것

BPMN, Temporal/Camunda 대체품, YAML 워크플로 엔진, 분산 사가 엔진, 휴먼 태스크 엔진이 아닙니다. JVM 하나 안에서 도는 작은 런타임입니다. 분산 트랜잭션이나 실행 리플레이가 필요하면 그쪽 도구를 쓰세요.

이 다섯 개만 알면 전체 구조가 잡힙니다.

Engine
최상위 컨테이너. Clock · EventBus · 리스너 · 체크포인트 저장소를 소유하고 Worker에게 나눠 줍니다.
Worker  스레드 1개

헷갈리는 지점 · Flow는 “정의”가 아니라 “실행 인스턴스”

실제로는 주문 1건 = Flow 객체 1개입니다. Step 인스턴스까지 매번 새로 만들어 붙입니다. 정의를 등록해 두는 저장소도, 정의 ID도 없습니다. “정의”에 해당하는 것은 여러분이 작성한 팩토리 메서드(코드) 그 자체입니다.

여기에 두 개를 더하면 전부입니다

03용어

문서에서 반복되는 말들입니다. 여기서 한 번 정리하고 넘어가면 뒤가 편합니다.

오케스트레이션orchestration
여러 개의 일을 순서와 조건에 맞게 지휘하는 것. 실제 일(결제 승인, DB 저장, HTTP 호출)은 도메인 서비스가 하고, Step은 “언제 무엇을 시키고 언제 다음으로 넘어갈지”만 결정합니다.
틱tick
Worker가 한 바퀴 도는 것. 한 틱에서 각 활성 Flow는 정확히 한 번 전진 기회를 얻습니다. 기본 100ms 간격.
FlowIdflowType + flowKey
"order" + "ORD-1024"처럼 종류와 인스턴스 키의 쌍. 중복 실행을 막는 기준값입니다.
터미널 상태terminal state
더 이상 전진하지 않는 최종 상태. FINISHED · FAILED · CANCELLED · CHECKPOINT_FAILED 네 가지입니다.
시그널signal
Step 하나에 국한된 이름표 있는 메모. 이벤트 핸들러(다른 스레드)가 남기고, 틱 스레드가 읽습니다. 스레드 경계를 넘기는 안전한 통로입니다.
가드Guard
“이 Step을 지금 돌려도 되나?”를 판단하는 짧은 함수. 통과·보류·우회·실패 중 하나를 반환합니다.
스냅샷snapshot
Flow의 현재 상태를 그 시점에 복사해 둔 불변 읽기 전용 뷰. 리스너와 덤프가 받습니다.
체크포인트checkpoint
durable Flow의 “현재 위치” 기록. 어떤 stepId에, stepNo 몇에, 진입했는지 여부까지만 담습니다.
멱등성idempotent
같은 작업을 여러 번 해도 결과가 한 번 한 것과 같은 성질. 복구 시 중요합니다.

“구현은 바깥에서 끼워 넣으라”고 정의만 해 둔 인터페이스. EventBus, Clock, FlowCheckpointStore가 그렇습니다.

045분 퀵스타트

복사해서 main()에 붙이면 도는 최소 예제입니다.

Maven
<dependency>
    <groupId>io.github.flowerjvm</groupId>
    <artifactId>flower-core</artifactId>
    <version>0.1.3</version>
</dependency>
OrderQuickStart.java
import io.github.flowerjvm.flower.core.engine.Engine;
import io.github.flowerjvm.flower.core.event.InMemoryEventBus;
import io.github.flowerjvm.flower.core.flow.Flow;
import io.github.flowerjvm.flower.core.step.Step;
import io.github.flowerjvm.flower.core.step.StepContext;
import io.github.flowerjvm.flower.core.step.StepResult;
import io.github.flowerjvm.flower.core.worker.Worker;

public class OrderQuickStart {

    // 1) Step: 한 단계의 일. onTick이 "다음에 뭘 할지"를 돌려준다.
    static final class AcceptStep extends Step {
        @Override protected void onEnter(StepContext ctx) {
            System.out.println("주문 접수: " + ctx.flowId().flowKey());
        }
        @Override protected StepResult onTick(StepContext ctx) {
            return StepResult.done();          // 이 Step 끝, 다음 Step으로
        }
    }

    static final class WaitPaymentStep extends Step {
        @Override protected void onEnter(StepContext ctx) {
            ctx.startTimeout(3_000);           // 3초 제한 시작
        }
        @Override protected StepResult onTick(StepContext ctx) {
            if (ctx.hasSignal("paid")) return StepResult.done();
            if (ctx.timedOut()) {
                return StepResult.fail(new IllegalStateException("payment 단계: 결제 시간 초과"));
            }
            return StepResult.stay();          // 아직 대기 중 — 다음 틱에 다시
        }
    }

    public static void main(String[] args) throws Exception {
        // 2) Worker: 틱 루프의 주인
        Worker worker = Worker.builder("orders").intervalMillis(30).build();

        // 3) Engine: 공용 서비스를 묶어 Worker에 주입
        Engine engine = Engine.builder()
                .eventBus(InMemoryEventBus.create())
                .worker(worker)
                .build();

        // 4) Flow: 이 주문 1건의 실행 계획. Step은 매번 새로 만든다.
        Flow flow = Flow.builder("order", "ORD-1024")
                .step("accept",  new AcceptStep())
                .step("payment", new WaitPaymentStep())
                .build();

        engine.start();                        // 여기서부터 틱이 돈다
        worker.submit(flow);                   // 다음 틱부터 실행 대상

        Thread.sleep(4_000);
        System.out.println("최종 상태 = " + flow.state());   // FAILED (결제 신호가 없었으므로)
        engine.stop();
    }
}

코드의미

05Flow가 진행되는 순서

위 예제가 틱 단위로 어떻게 움직이는지. 이 표 하나가 Flower의 실행 감각 전부입니다.

시점Flow 상태현재 Step일어나는 일
submitREADY—Worker가 Flow를 받아 대기 큐에 넣습니다. 아직 아무 Step도 실행되지 않습니다.
tick 1RUNNINGaccept ① 활성 목록에 등록, onFlowSubmitted 발화
② onEnter(accept)
③ 같은 틱에 이어서 onTick(accept) → done()
④ onExit(accept), 다음 Step으로 이동
tick 2RUNNINGpaymentonEnter(payment)(타임아웃 시작) → onTick(payment) → 신호 없음 → stay()
tick 3…nRUNNINGpaymentonTick만 반복. onEnter는 다시 호출되지 않습니다.
(외부)RUNNINGpayment결제 이벤트가 다른 스레드에서 도착 → 핸들러가 ctx.signal("paid")만 남기고 즉시 반환
tick n+1FINISHED—onTick이 신호 발견 → done() → onExit(구독 자동 해제) → 다음 Step 없음 → 종료 + onFlowFinished 발화

여기서 얻어갈 세 가지

1. 진입과 첫 틱은 같은 틱

onEnter 직후 곧바로 onTick이 한 번 호출됩니다. 그래서 “진입하자마자 끝나는 Step”은 1틱에 통과합니다.

2. Step 전환에 1틱이 든다

done()으로 나간 뒤 다음 Step의 onEnter는 그 다음 틱입니다. Step이 10개면 최소 10틱(기본 1초)입니다.

3. 외부 스레드는 신호만 남긴다

이벤트 핸들러는 시그널만 세우고 끝냅니다. 실제 전이는 항상 틱 스레드의 onTick이 결정합니다. Step 코드에 동기화가 필요 없는 이유입니다.

헷갈리는 지점 · “100ms마다”가 아니라 “끝난 뒤 100ms”

이렇게 보입니다 intervalMillis(100)이니 정확히 100ms 주기로 틱이 돈다.

실제로는 고정 지연입니다. 한 틱이 40ms 걸렸다면 다음 틱은 그로부터 100ms 뒤 — 실제 주기는 140ms가 됩니다. 대신 밀린 틱이 몰아서 실행되는 일은 없습니다. 틱이 무거워지면 전체가 느려질 뿐 폭주하지 않습니다.

틱 간격 고르기

간격은 지연 시간과 CPU의 트레이드오프입니다. 사람이 기다리는 흐름이면 20~50ms, 초 단위로 진행되는 배치성 흐름이면 200~1000ms가 적당합니다. 다만 간격보다 훨씬 중요한 것은 느린 Step 하나가 같은 Worker의 모든 Flow를 지연시킨다는 점입니다.

그래서 Flow는 팩토리 메서드로 만드는 것이 관례입니다 — 필요할 때마다 새로 조립할 수 있으니까요.

언제 무엇이 호출되는지. 훅은 네 개뿐입니다.

훅필수언제 불리나
onEnter(ctx)선택이 Step이 현재가 된 직후 한 번. 외부 작업 시작 · 이벤트 구독 · 타임아웃 시작 자리.
onTick(ctx)필수현재인 동안 매 틱. StepResult를 반드시 반환합니다.
onExit(ctx)선택Step을 떠날 때(done · goTo · finish · fail · cancel). repeat에서는 호출되지 않습니다.
onReset(ctx)선택repeat() 시. 프레임워크가 구독·시그널·타임아웃·stepNo를 먼저 정리한 뒤에 호출됩니다.

훅별 “해야 할 일 / 하면 안 되는 일”

훅해야 할 일하면 안 되는 일
onEnter 외부 작업 시작(비동기 호출 발사), ctx.subscribe(...), ctx.startTimeout(...) 결과를 기다리는 블로킹 호출. 여기서 예외를 던지면 onExit 없이 Flow가 실패합니다.
onTick 시그널 · 도메인 상태 · 타임아웃 확인, 짧은 판단, StepResult 반환 sleep, 동기 HTTP·DB 대기, 폴링 루프. 여기서 1초를 쓰면 그 Worker의 모든 Flow가 1초 늦습니다.
onExit 이 Step이 만든 자원 해제, 완료 이벤트 발행, 결과 기록 실패할 수 있는 작업을 방치하는 것 — 여기서 예외가 나면 성공이 실패로 뒤집힙니다.
onReset 인스턴스 필드 초기화(재시도 카운터 등) 구독·시그널·타임아웃·stepNo 정리 — 이미 프레임워크가 했습니다.
헷갈리는 지점 · 첫 onTick은 “아직 아무것도 없는” 시점입니다

이렇게 보입니다 onEnter에서 외부 호출을 시작했으니, 첫 onTick에서는 결과를 받아 처리하면 되겠다.

실제로는 onEnter 직후 같은 틱에 onTick이 무조건 한 번 호출됩니다. 그 순간 외부 응답이 도착해 있을 가능성은 거의 없습니다. 첫 onTick이 “아직 없음 → stay()”로 끝나는 것이 정상 경로이며, “당연히 왔겠지”를 전제로 null 체크를 빼면 그대로 NPE입니다.

Step 인스턴스를 공유하지 마세요

Step은 Flow 하나에 속한 상태 있는 객체입니다. 새 Flow를 만들 때마다 new로 만드세요. 스프링 싱글턴 빈으로 등록해 여러 Flow가 공유하면 필드가 뒤섞입니다.

08StepResult — 6가지 전이

Flow를 움직이는 유일한 수단입니다.

결과의미부수 동작
stay()이 Step 유지, 다음 틱에 다시 호출아무 일도 하지 않음(가장 저렴). 대기의 표준 표현.
done()이 Step 완료 → 다음에 선언된 SteponExit 호출 + 구독 해제. 마지막이면 Flow가 FINISHED.
repeat()이 Step을 처음부터 다시onExit 대신 onReset. 구독·시그널·타임아웃 해제, stepNo=0. 다음 틱에 onEnter부터.
goTo("id")임의의 stepId로 점프(앞/뒤 무관)onExit 호출 후 이동. 없는 id면 Flow가 실패합니다.
finish()남은 Step을 건너뛰고 성공 종료onExit 호출 후 FINISHED.
fail(cause)Flow 전체를 실패로 종료onExit 호출 후 FAILED. cause는 null 불가.
헷갈리는 지점 · done()과 finish()는 언제 다른가

이렇게 보입니다 마지막 Step에서 done()을 반환해도 Flow가 FINISHED가 되니 finish()와 같은 것 아닌가?

실제로는 마지막 Step에서만 결과가 같고, 의미와 확장성이 다릅니다.

· done() = “이 Step이 끝났다” → 다음 Step이 있으면 그리로. 나중에 Step을 추가하면 자연스럽게 이어집니다.
· finish() = “Flow 전체가 끝났다” → 뒤에 Step이 몇 개든 건너뜁니다. Step을 추가해도 계속 거기서 끝납니다.

정상 완료는 웬만하면 done(), finish()는 “조건이 충족돼 남은 단계가 필요 없어진 경우”에만 쓰세요.

헷갈리는 지점 · repeat() vs goTo(자기 자신)

이렇게 보입니다 둘 다 “이 Step을 다시 실행”이니 아무거나 써도 된다.

실제로는 거쳐 가는 훅이 다릅니다.

· repeat() → onReset → (다음 틱) onEnter. onExit는 호출되지 않습니다.
· goTo("자기 id") → onExit → (다음 틱) onEnter. onReset은 호출되지 않습니다.

onExit에 “완료 처리”나 “완료 이벤트 발행”이 들어 있다면 goTo(self)는 돌 때마다 그것을 실행합니다. 재시도는 repeat()를 쓰세요.

헷갈리는 지점 · goTo로 되돌아온 Step은 필드가 초기화되지 않습니다

이렇게 보입니다 goTo로 앞 Step에 다시 들어가면 onEnter부터 다시 시작하니 “새것”처럼 동작하겠지.

실제로는 Step 인스턴스는 같은 객체 그대로이고, goTo 경로에서는 onReset이 호출되지 않습니다(onReset은 repeat() 전용).

· 초기화됨 — stepNo, 시그널, 구독, 타임아웃
· 초기화 안 됨 — 여러분이 Step에 선언한 인스턴스 필드 전부

final class ChargeStep extends Step {
    private int attempts;          // ← goTo로 다시 와도 0으로 안 돌아간다

    @Override protected void onEnter(StepContext ctx) {
        attempts = 0;              // ✓ 진입할 때마다 직접 초기화하는 것이 안전
    }
}

루프를 만드는 goTo(예: verify → retry-wait → verify)에서 특히 자주 물립니다.

onExit에서 예외가 나면 성공이 실패로 뒤집힙니다

done()이었어도 onExit가 예외를 던지면 Flow는 FAILED가 됩니다. onExit에는 실패해도 되는 정리만 넣고, 반드시 성공해야 하는 작업은 onTick에서 처리한 뒤 결과를 반환하세요.

goTo("payment")의 오타는 런타임에야 발견됩니다. enum으로 감싸면 컴파일 타임에 잡힙니다.

10기다리기: 이벤트 · 시그널 · 타임아웃

Flower에서 “기다림”을 표현하는 방법. 스레드를 붙잡지 않는 것이 핵심입니다.

표준 패턴

onEnter에서 구독 → onTick에서 확인
final class WaitForPaymentStep extends Step {

    @Override protected void onEnter(StepContext ctx) {
        ctx.startTimeout(30_000);                       // 30초 제한
        ctx.subscribe(PaymentApproved.class, event -> { // 구독은 자동 해제된다
            if (event.orderId().equals(ctx.flowId().flowKey())) {
                ctx.signal("paid", event);              // 신호만 남기고 즉시 반환
            }
        });
    }

    @Override protected StepResult onTick(StepContext ctx) {
        PaymentApproved approved = ctx.consumeSignal("paid", PaymentApproved.class);
        if (approved != null) {
            orderService.markPaid(approved);            // 실제 처리는 틱 스레드에서
            return StepResult.done();
        }
        if (ctx.timedOut()) {
            return StepResult.fail(new IllegalStateException("payment 단계: 결제 승인 시간 초과"));
        }
        return StepResult.stay();
    }
}

ctx.subscribe(...)로 만든 구독은 Step이 끝나거나 리셋되면 프레임워크가 자동으로 해제합니다. 직접 해제할 필요가 없고, 누수도 생기지 않습니다.

같은 이름의 시그널이 한 틱 사이에 세 번 오면 마지막 하나만 남습니다. “모든 이벤트를 하나도 빠짐없이 처리”해야 한다면 시그널이 아니라 도메인 저장소나 사용자 소유의 큐를 쓰고, 시그널은 “확인해 보라”는 깨움 신호로만 쓰세요.

실제로는 시그널은 Step 하나의 범위입니다. Step을 나가면 사라지고 다음 Step은 절대 볼 수 없습니다.

subscribe(PaymentEvent.class, ...)는 PaymentApproved extends PaymentEvent를 받지 못합니다. 런타임 타입이 정확히 일치해야 합니다. 이벤트는 구체적이고 불변인 최종 클래스로 만드는 것이 안전합니다.

타임아웃

API동작
startTimeout(ms)제한 시간 시작. 다시 호출하면 덮어씁니다. 음수는 예외. durable Flow에서는 사용 불가
timedOut()시간이 지났는지. 시작한 적 없으면 항상 false
elapsedMillis()시작 이후 경과. 시작한 적 없으면 0
헷갈리는 지점 · startTimeout은 타이머를 걸지 않습니다

이렇게 보입니다 startTimeout(30_000)을 호출해 뒀으니 30초가 지나면 프레임워크가 무언가 해 줄 것이다.

실제로는 스레드도 콜백도 예약 작업도 없습니다. timedOut()을 호출하는 그 순간 시간을 계산할 뿐입니다. 따라서 onTick에서 timedOut()을 확인하지 않으면 아무 일도 일어나지 않고 영원히 stay()합니다.

durable Flow에서는 startTimeout을 쓸 수 없습니다

타임아웃 상태는 체크포인트에 저장되지 않기 때문입니다. 허용했다면 재시작 후 “30초 남았던 마감이 조용히 처음부터 다시”가 됩니다. 조용한 오작동 대신 즉시 예외를 택한 설계입니다. durable 흐름에서는 마감 시각을 도메인 상태에 저장하고 ctx.clock().currentTimeMillis()와 비교하세요.

11Step 사이에서 값 공유하기

여기서 실수하면 코드가 빠르게 나빠집니다.

stepId (문자열)
  • Flow 전체에서의 위치 이름
  • goTo("payment")의 대상
  • 로그·덤프·체크포인트에 그대로 노출
stepNo (정수)
  • Step 내부의 작은 커서
  • “요청 보냄 → 응답 확인” 정도의 미세 단계

이러면 Step을 쪼개세요

stepNo가 WAITING_PAYMENT, RETRYING 같은 비즈니스 상태를 표현하기 시작하면 그건 Step으로 나누라는 신호입니다.

값 공유는 이렇게

“이 실행이 누구의 어떤 런인가”를 담는 작은 신분증입니다. 비즈니스 컨텍스트가 아닙니다.

12Durable Flow — 체크포인트와 재개

프로세스가 죽었다 살아나도 흐름을 이어가는 방법. 먼저 기대치를 정확히 맞추는 것이 중요합니다.

저장되는 것
  • 어느 Step에 있었는지
  • 진입까지 했는지
  • Step 내부 커서 stepNo
  • 실행 신원(runId, traceId 등)
  • 정의 버전
저장되지 않는 것
  • Step 인스턴스의 필드
  • 진행 중이던 이벤트·시그널
  • startTimeout 상태
  • 부수효과의 실행 여부
그래서 규칙은 하나

재시작 후에도 필요한 값은 전부 도메인 저장소에. 체크포인트는 “어디까지 왔나”만 알려 주는 책갈피입니다.

헷갈리는 지점 · durable 설정 오류는 서로 다른 시점에 터집니다

이렇게 보입니다 durable 설정이 잘못됐으면 build()에서 다 잡아 주겠지.

실제로는 검사 주체가 달라 터지는 시점도 다릅니다.

· 복구 정책 없는 Step → build()에서 예외
· 저장소 미연결 → build()는 통과하고 submit()에서 예외

“테스트에서는 잘 만들어졌는데 제출할 때 터진다”가 정상 동작입니다. 통합 테스트에서 제출까지 해 봐야 잡힙니다.

멱등성이 전제 조건입니다

체크포인트는 “진입했다”까지만 기억합니다. 진입 도중 어디까지 부수효과가 나갔는지는 모릅니다. 그래서 복구 시 onEnter가 다시 실행될 수 있고, 결제 요청이 두 번 나갈 수 있습니다. 외부 호출에는 반드시 멱등 키를 쓰거나, 먼저 도메인 상태를 조회해 “이미 했는지” 확인하세요.

재시작 후 복구하기

자동이 아니라 애플리케이션이 명시적으로 호출합니다.

시작 시 복구
FlowFactoryRegistry registry = FlowFactoryRegistry.builder()
        .register("order", id -> orderFlowFactory.create(id.flowKey()))
        .build();

log.info("복구된 Flow 수 = {}", restored);

복구는 저장된 위치를 읽어 → Flow를 새로 조립하고 → 그 위치부터 재개하는 흐름입니다. Flower가 과거 실행을 재생하지 않습니다.

여러 프로세스에서 복구할 때

Flower의 중복 실행 방지는 Engine 하나, JVM 하나 안에서만 유효합니다. 같은 저장소를 보는 인스턴스가 2대라면 둘 다 같은 체크포인트를 읽어 같은 Flow를 동시에 복구할 수 있습니다. 리더 선출 · DB 행 잠금 · 리스 중 하나를 애플리케이션이 직접 적용하세요. findActiveByWorker(name)로 워커 이름을 인스턴스별로 구분하는 것도 실무적인 완화책입니다.

알아둘 두 가지
  • 체크포인트 저장은 틱 경로에서 동기로 일어납니다. 느린 저장소는 곧 느린 Flow입니다.
  • 저장에 실패하면 Flow가 CHECKPOINT_FAILED로 멈춥니다. “위치를 저장하지 못했는데 계속 전진”하면 재시작 시 부수효과가 중복되므로, 조용히 진행하는 대신 즉시 멈추고 크게 알리는 쪽을 택한 설계입니다. 이때 onFlowFailed가 호출됩니다.

돌아가는 것을 밖에서 들여다보는 방법. 세 단계가 있습니다.

1단계 — FlowerListener

생명주기 훅

· 예외 메시지에 Step 이름을 직접 담기 — 가장 간단하고 확실합니다

return StepResult.fail(new IllegalStateException("payment 단계: 결제 승인 없음"));

14테스트

Flower의 가장 큰 실용적 장점입니다. 스레드도, 대기도, 플래키 테스트도 없습니다.

핵심은 두 가지 — engine.attach()만 호출해 스케줄러를 띄우지 않고, worker.tickOnce()로 시간을 직접 진행시키는 것입니다.

기본 패턴
@Test
void 결제_신호가_오면_완료된다() {
    ManualClock clock = new ManualClock();
    InMemoryEventBus bus = InMemoryEventBus.create();
    Worker worker = Worker.builder("test").build();

    Engine engine = Engine.builder()
            .clock(clock).eventBus(bus).worker(worker).build();
    engine.attach();                    // start() 아님! 스케줄러 없이 붙이기만

    Flow flow = Flow.builder("order", "ORD-1")
            .step("accept",  new AcceptStep())
            .step("payment", new WaitPaymentStep())
            .build();

    worker.submit(flow);
    worker.tickOnce();                  // 제출 반영 + accept 진입/완료
    worker.tickOnce();                  // payment 진입 + 첫 onTick

    assertThat(flow.currentStepId()).isEqualTo("payment");

    bus.publish(new PaymentApproved("ORD-1"));   // 동기 발행 → 즉시 반영
    worker.tickOnce();

    assertThat(flow.state()).isEqualTo(FlowState.FINISHED);
}

@Test
void 시간이_지나면_실패한다() {
    // … 동일한 준비 …
    worker.tickOnce();
    worker.tickOnce();                  // payment 진입, startTimeout(30_000)

    clock.advance(30_000);              // 30초를 즉시 통과
    worker.tickOnce();

    assertThat(flow.state()).isEqualTo(FlowState.FAILED);
}

체크리스트
  • engine.start()를 테스트에서 쓰지 마세요. 썼다면 tickOnce()가 예외를 던집니다.
  • 시간이 관여하는 검증은 전부 ManualClock.advance()로. Thread.sleep은 필요 없습니다.
  • 이벤트는 InMemoryEventBus.publish()로 테스트 스레드에서 직접 발행 — 동기 디스패치라 즉시 반영됩니다.
  • tickOnce()는 테스트나 호스트 제어 스레드에서만 부르세요. Step·Guard·리스너 안에서 부르면 예외입니다.

engine.start()를 호출했는지 확인하세요. attach()만 했다면 틱이 돌지 않으므로 worker.tickOnce()를 직접 불러야 합니다.
tickOnce()가 예외를 던집니다
이미 start()로 스케줄러가 돌고 있는 Worker입니다. 테스트에서는 engine.attach()까지만 하세요. 또는 Step·리스너 안에서 부른 재진입 상황입니다.
이벤트를 발행했는데 Step이 못 받아요
① 정확한 런타임 타입으로 구독했는가(상위 타입 구독은 동작하지 않음) ② 구독이 onEnter에서 이루어졌고 그 Step이 현재 Step인가 ③ 이벤트가 같은 EventBus로 발행되었는가.
onExit가 안 불려요
repeat() 경로이거나(onReset이 대신 불립니다), onEnter에서 예외가 났거나, durable Flow가 Worker 정지로 보존된 경우입니다.
done()을 반환했는데 Flow가 실패했어요
onExit에서 예외가 났을 가능성이 큽니다. 성공이 실패로 뒤집히는 유일한 경로입니다.
durable Flow를 제출하니 예외가 납니다
① 체크포인트 저장소가 없거나 ② 복구 정책이 없는 Step이 섞여 있습니다. 후자는 build()에서, 전자는 submit()에서 납니다.
durable Flow에서 startTimeout이 예외를 던집니다
의도된 동작입니다. 타임아웃은 체크포인트에 저장되지 않기 때문입니다. 마감 시각을 도메인 상태에 저장하고 ctx.clock().currentTimeMillis()와 비교하세요.
같은 주문에 대해 Flow가 두 번 돌아요
같은 FlowId라면 한 Engine 안에서는 막힙니다. 두 프로세스가 각각 복구했다면 애플리케이션 레벨의 락이나 리더 선출이 필요합니다.
Flow가 느립니다
Step 개수 × 틱 간격이 최소 소요 시간입니다(Step 10개 · 100ms = 최소 1초). 간격을 줄이거나 Step을 합치세요. 그리고 같은 Worker에 느린 Step이 있는지 먼저 의심하세요.
Engine.stop() 후 다시 start()가 안 됩니다
Engine과 Worker는 재사용할 수 없습니다. 새로 만드세요. 일시 중지는 pause()/resume()을 쓰세요.

기억해야 할 10가지

  1. 한 틱에 각 Flow는 한 번만 전진한다.
  2. onEnter와 첫 onTick은 같은 틱에 일어난다.
  3. Step 전환에는 1틱이 든다.
  4. onTick은 절대 블로킹하지 않는다 — 같은 Worker의 모든 Flow가 함께 멈춘다.
  5. 외부 스레드는 시그널만 남긴다. 상태는 틱 스레드가 바꾼다.
  6. 이벤트 구독은 정확한 런타임 타입으로만 매칭된다.
  7. repeat()은 onExit가 아니라 onReset을 부른다.
  8. onExit에서 예외가 나면 성공이 실패로 뒤집힌다.
  9. durable은 위치만 저장한다. 나머지는 도메인 저장소에.
  10. Guard는 진입 여부와 무관하게 매 틱 평가된다.
