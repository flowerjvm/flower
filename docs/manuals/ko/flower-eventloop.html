Flower EventLoop

“주기적으로 깨워서 물어보는” 대신 “깨울 이유를 미리 선언하고 잠드는” 실행 방식. LLM 응답, 도구 호출, 사람의 승인처럼 언제 올지 모르는 것을 기다리는 흐름을 위한 별도 런타임입니다.

먼저 알아두세요 · MVP

이 모듈은 MVP입니다. 써 볼 만큼은 되지만 flower-core보다 API가 더 움직일 수 있습니다. 그리고 틱 기반 Worker를 대체하는 것이 아니라 별개의 실행 라인입니다. 둘 중 하나를 고르는 것이지 상위 호환이 아닙니다.

왜 두 번째 런타임이 필요했는지, 그리고 가장 작은 예제 하나.

01왜 두 번째 런타임인가

한 문장: “기다림”을 폴링이 아니라 구독으로 바꾼 Flower 런타임입니다.

틱 방식의 한계

flower-core의 Worker는 100ms마다 살아 있는 모든 Flow를 깨워 onTick()을 부릅니다. Step은 “아직이야”(stay())라고 답하고 다시 잠듭니다. 단순하고 테스트하기 좋은 모델입니다.

그런데 이런 상황을 생각해 보세요.

  • LLM 응답을 30초 기다리는 Flow가 1,000개
  • 사람의 승인을 3일 기다리는 Flow가 200개

틱 방식이라면 100ms마다 1,200번의 onTick()이 호출되고 그 대부분은 “아직”이라는 답만 하고 끝납니다. 게다가 응답이 도착해도 최대 100ms를 더 기다려야 발견됩니다.

해법: 깨울 이유를 미리 선언한다

이벤트 루프에서는 Step이 “나중에 또 물어봐”라고 하지 않습니다. 대신 “이 조건 중 하나가 충족되면 그때 깨워”라고 선언하고 완전히 잠듭니다.

이 모듈의 핵심 한 줄
return EventStepResult.await(
        AwaitCondition.event(LlmResponded.class),   // 이 이벤트가 오면 깨워줘
        AwaitCondition.deadlineIn(30_000))          // 아니면 30초 뒤에 깨워줘
        .thenPublish(new LlmRequested("hello"));    // 그리고 나서 이 요청을 보내줘

대기 중인 Flow는 CPU를 전혀 쓰지 않습니다. 이벤트가 도착하는 그 순간 깨어나므로 지연도 없습니다. Flow가 1,000개든 100,000개든 대기 비용이 거의 늘지 않습니다.

어떤 일에 맞나

상황왜 이벤트 루프인가
LLM · 에이전트 턴응답이 언제 올지 모릅니다. 도착 즉시 진행해야 하고 타임아웃도 필요합니다.
도구(tool) 호출 대기callId 같은 상관 키로 응답을 맞춰야 합니다.
사람의 승인며칠이 걸릴 수 있습니다. 그동안 폴링은 완전한 낭비입니다.
외부 콜백 · 웹훅언제 올지 모르는 단발성 응답.
대기 Flow가 매우 많은 경우대기 비용이 Flow 수에 비례해 늘지 않습니다.
반대로 이런 건 Core가 낫습니다
  • 주기적으로 확인해야 하는 일 — “DB 상태가 바뀌었나?”처럼 깨울 이벤트가 없는 작업. 이벤트 루프에서는 마감을 반복해 거는 어색한 코드가 됩니다.
  • 단계마다 짧게 끝나는 흐름 — 기다림이 없으면 이점이 없습니다.
  • 안정성이 최우선인 코드 — Core는 안정화된 API, 이벤트 루프는 MVP입니다.

02core와 무엇이 다른가

Core를 아신다면 이 표 하나가 문서의 절반입니다. 나머지는 이 차이의 결과입니다.

Flower CoreFlower EventLoop관계
Engine없음EventWorker가 스스로 최상위입니다. Clock·EventBus를 직접 지정하고 직접 start/stop 합니다.
WorkerEventWorker틱 루프 → 큐 리액터.
FlowEventFlow둘 다 “Step 순서 + 현재 위치”. FlowState는 공유합니다.
StepEventSteponTick이 없고 onEvent/onTimeout/onRecover가 있습니다.
StepResultEventStepResultstay()가 없고 await(...)가 대신합니다. done()은 next()로 이름이 바뀌었습니다.
Guard없음진입 조건은 onEnter에서 판단해 goTo하면 됩니다.
RecoveryPolicyonRecover 훅정책 열거형 대신 훅 하나. 기본 동작은 실패입니다.
worker.tickOnce()worker.drain()테스트 구동 방식. ManualClock과 함께 쓰는 것은 동일합니다.
FlowerListenerFlowerListener그대로 재사용합니다. 트레이스 스키마도 공유합니다.
헷갈리는 지점 · EventWorker는 Engine에 넣을 수 없습니다

이렇게 보입니다 같은 Flower니까 Engine.builder().worker(eventWorker)로 함께 관리하면 되겠다.

실제로는 Engine.worker(...)는 Core의 Worker 타입만 받습니다. Clock·EventBus·리스너·저장소를 EventWorker 빌더에 직접 주고 start()/stop()도 직접 호출해야 합니다.

두 런타임을 한 애플리케이션에서 같이 쓸 수는 있습니다. 같은 EventBus 인스턴스를 공유시키면 서로 이벤트를 주고받을 수 있습니다.

03퀵스타트

LLM 호출을 기다리는 흐름. 복사해서 바로 돌려볼 수 있습니다.

Maven
<dependency>
    <groupId>io.github.flowerjvm</groupId>
    <artifactId>flower-eventloop</artifactId>
    <version>0.1.3</version>
</dependency>
LlmQuickStart.java
import io.github.flowerjvm.flower.core.event.InMemoryEventBus;
import io.github.flowerjvm.flower.core.time.SystemClock;
import io.github.flowerjvm.flower.eventloop.flow.EventFlow;
import io.github.flowerjvm.flower.eventloop.step.*;
import io.github.flowerjvm.flower.eventloop.worker.EventWorker;

public class LlmQuickStart {

    // 주고받을 이벤트 — 불변 클래스로 (정확한 타입 매칭이 됩니다)
    static final class LlmRequested { final String prompt;
        LlmRequested(String p) { this.prompt = p; } }
    static final class LlmResponded { final String text;
        LlmResponded(String t) { this.text = t; } }

    // onTick이 없다. 대신 "무엇이 오면 깨울지"를 선언한다.
    static final class AskStep extends EventStep {
        @Override protected EventStepResult onEnter(EventStepContext ctx) {
            return EventStepResult
                    .await(AwaitCondition.event(LlmResponded.class),   // 응답이 오거나
                           AwaitCondition.deadlineIn(30_000))          // 30초가 지나거나
                    .thenPublish(new LlmRequested("안녕?"));           // ← 구독 후에 발행된다
        }

        @Override protected EventStepResult onEvent(EventStepContext ctx, Object event) {
            LlmResponded res = (LlmResponded) event;
            System.out.println("응답: " + res.text);
            return EventStepResult.next();           // 다음 Step으로
        }

        @Override protected EventStepResult onTimeout(EventStepContext ctx) {
            return EventStepResult.goTo("fallback");  // 30초 초과 → 대체 경로
        }
    }

    static final class DoneStep extends EventStep {
        private final String label;
        DoneStep(String label) { this.label = label; }
        @Override protected EventStepResult onEnter(EventStepContext ctx) {
            System.out.println("종료: " + label);
            return EventStepResult.finish();
        }
    }

    public static void main(String[] args) throws Exception {
        InMemoryEventBus bus = InMemoryEventBus.create();

        // Engine이 없다. Clock과 EventBus를 직접 준다. 둘 다 필수.
        EventWorker worker = EventWorker.builder("llm")
                .clock(SystemClock.INSTANCE)
                .eventBus(bus)
                .build();

        // 바깥 세상: 요청을 받아 실제로 모델을 부르는 쪽 (여기서는 흉내만)
        bus.subscribe(LlmRequested.class, req -> bus.publish(new LlmResponded("반가워!")));

        EventFlow flow = EventFlow.builder("llm-call", "req-1")
                .step("ask",      new AskStep())
                .step("complete", new DoneStep("정상 완료"))
                .step("fallback", new DoneStep("타임아웃 대체"))
                .build();

        worker.start();            // 데몬 스레드 하나 기동
        worker.submit(flow);

        Thread.sleep(500);
        worker.stop();
    }
}

Core 코드와 다른 곳

여기Core였다면
EventWorker.builder(...)
.clock(...).eventBus(...)		Engine이 Clock·EventBus를 갖고 Worker에 나눠 줬습니다. 여기서는 워커가 직접 받습니다(둘 다 필수).
onEnter가 결과를 반환Core의 onEnter는 void였습니다. 여기서는 반드시 EventStepResult를 반환합니다.
await(...)stay(). “나중에 또 물어봐” vs “이게 오면 깨워”의 차이입니다.
.thenPublish(...)Core에서는 onEnter 안에서 그냥 발행했습니다. 여기서 그러면 응답을 놓칠 수 있습니다. → 07장
onEvent / onTimeoutsubscribe + 시그널 + onTick 확인. 세 단계가 하나로 줄었습니다.
next()done(). 이름만 다르고 의미는 같습니다.

실행 순서

순번내용
1submit(flow) — 워커가 Flow를 받고 “첫 Step 진입”을 예약합니다.
2onEnter(ask) 호출 → await(...) 반환
3① LlmResponded 구독 등록 ② 30초 마감 등록 ③ (durable이면) 체크포인트 저장
4그 다음에야 thenPublish 효과 실행 → 요청 발행
5응답이 도착하면 onEvent 호출 → next()
6onExit(ask) → 구독·마감 전부 해제 → 다음 Step 진입
헷갈리는 지점 · 대기 중인 Flow는 “실행 중”이 아닙니다

이렇게 보입니다 응답 대기 상태에서 워커는 그 Flow를 계속 돌보고 있을 것이다.

실제로는 워커는 그 Flow를 완전히 잊고 있습니다. 남아 있는 것은 이벤트 구독 하나와 마감 항목 하나뿐입니다. 그 둘 중 하나가 깨우기 전까지 이 Flow에 대해 실행되는 코드는 단 한 줄도 없습니다.

그래서 대기 Flow가 10만 개여도 CPU 사용량은 0에 가깝습니다. 대신 “아무도 깨워주지 않으면 영원히 잠듭니다” — 마감 없는 await가 위험한 이유입니다.

04EventStep 생명주기

훅은 다섯 개. 그중 둘은 기본 동작이 “실패”라 반드시 알아야 합니다.

훅필수반환언제
onEnter(ctx)필수EventStepResult이 Step이 현재가 된 직후 1회. 보통 await(...)를 반환합니다.
onEvent(ctx, event)선택결과 또는 null대기 조건에 걸린 이벤트가 도착했을 때. 기본 구현은 null(무시하고 계속 대기).
onTimeout(ctx)선택결과 또는 null마감 도래. 기본 구현은 실패
onRecover(ctx, recovery)durable이면 필수EventStepResult체크포인트에서 복원될 때 onEnter 대신. 기본 구현은 실패
onExit(ctx)선택voidStep을 떠날 때.
헷갈리는 지점 · 같은 null인데 훅마다 뜻이 다릅니다

이렇게 보입니다 결과를 반환하지 않으면 다 똑같이 처리되겠지.

실제로는 세 갈래입니다.

· onEnter가 null → Flow 실패
· onEvent가 null → 이 이벤트를 무시하고 기존 대기 유지. 정상적인 사용법입니다.
· onTimeout이 null → 마감만 제거하고 이벤트 대기는 계속 유지

onEvent에서 null을 반환하는 건 “내가 기다리던 그 이벤트가 아니다”를 표현하는 정식 방법입니다. 여러 타입을 함께 기다릴 때 유용합니다.

기본 구현이 “실패”인 두 훅

onTimeout과 onRecover는 재정의하지 않으면 흐름을 실패시킵니다. 실수를 조용히 넘기지 않으려는 의도적 설계입니다. deadlineIn(...)을 걸었으면 onTimeout을, durable()을 붙였으면 onRecover를 반드시 구현하세요.

05EventStepResult

결과의미부수 동작
await(c1, c2, ...)이 Step을 유지하고 조건 중 하나가 오면 깨어남기존 대기 전부 해제 → 새로 등록 → 효과 실행. 조건이 0개면 예외.
next()이 Step 완료 → 다음 SteponExit 호출, 대기 해제. 마지막이면 FINISHED. (Core의 done())
goTo("id")임의의 stepId로 점프onExit 호출, 대기 해제. 없는 id면 실패.
finish()남은 Step을 건너뛰고 성공 종료onExit → FINISHED
fail(cause)Flow 실패 종료onExit → FAILED
헷갈리는 지점 · await는 추가가 아니라 “통째로 교체”입니다

이렇게 보입니다 onEvent에서 await(event(B.class))를 반환하면 기존 A 대기에 B가 추가되겠다.

실제로는 기존 대기가 전부 해제되고 B만 남습니다. 마감도 함께 사라집니다.

A와 B를 둘 다 기다리려면 한 번에 전부 다시 선언해야 합니다.

// ✕ B만 남고 A와 마감은 사라짐
return EventStepResult.await(AwaitCondition.event(B.class));

// ✓ 계속 기다릴 것을 전부 다시 선언
return EventStepResult.await(
        AwaitCondition.event(A.class),
        AwaitCondition.event(B.class),
        AwaitCondition.deadlineIn(remainingMillis));   // 남은 시간도 직접 계산

마감은 “등록 시점부터 다시” 계산됩니다. 매번 deadlineIn(30_000)을 넣으면 이벤트가 올 때마다 마감이 30초씩 연장되는 셈이니, 전체 마감을 지키려면 ctx.now()로 남은 시간을 직접 계산하세요.

06AwaitCondition — 대기 조건

“무엇이 오면 깨울지”를 선언하는 세 가지 방법.

생성깨우는 것비고
event(Foo.class)Foo가 발행될 때정확한 런타임 타입 일치만. 하위 클래스는 걸리지 않습니다.
event(Foo.class, predicate)타입 일치 + 조건 통과“내 주문 것만” 같은 필터. durable에서는 사용 불가
signal("tool-call", callId)같은 이름·키의 신호이름과 키 모두 필수. durable에서도 안전합니다.
deadlineIn(30_000)등록 시점 기준 30초 후음수면 예외. 0이면 즉시 만료.
헷갈리는 지점 · 마감을 여러 개 걸면 하나로 합쳐집니다

이렇게 보입니다 await(event(A), deadlineIn(5000), event(B), deadlineIn(30000))처럼 조건별로 다른 타임아웃을 줄 수 있겠다.

실제로는 가장 이른 마감 하나만 남고 나머지는 버려집니다. 위 예에서는 5초 하나만 살아남고, 5초 뒤 onTimeout이 한 번 호출됩니다. “어느 조건의 타임아웃인지”는 알 수 없습니다.

단계별로 다른 마감이 필요하면 Step을 나누거나, 짧은 마감으로 깨어난 뒤 onTimeout에서 다시 await(...)를 걸어 남은 시간을 재선언하세요.

헷갈리는 지점 · 타임아웃이 나도 이벤트 대기는 살아 있습니다

이렇게 보입니다 타임아웃이 발생하면 그 Step의 대기가 전부 끝나는 것 아닌가.

실제로는 onTimeout이 null을 반환하면 마감만 제거되고 이벤트·시그널 대기는 그대로 유지됩니다. “일단 마감은 지났지만 응답은 계속 기다린다”를 표현하는 정식 방법입니다.

@Override protected EventStepResult onTimeout(EventStepContext ctx) {
    alertService.warn("응답 지연: " + ctx.flowId());
    return null;      // 마감만 소멸, 응답 대기는 계속
}

반대로 기본 구현은 실패라 아무것도 재정의하지 않으면 흐름이 죽습니다.

깨우기가 조용히 무시되는 경우

이벤트를 분명히 보냈는데 아무 일도 안 일어난다면 이걸 확인하세요.

  • 런타임 타입이 정확히 일치하지 않음(상위 타입 대기는 동작하지 않음)
  • 시그널의 이름 또는 키가 다름
  • 그 Step이 이미 다른 await로 교체했거나 다음 Step으로 넘어감
  • 같은 EventBus 인스턴스가 아님

무시는 조용히 이루어집니다. 로그도 남지 않습니다.

07효과 — 순서가 중요한 이유

thenPublish가 왜 있는지, 그리고 그것이 무엇을 보장하지 않는지.

onEnter 안에서 그냥 publish하면 안 되는 이유

InMemoryEventBus는 동기입니다. 발행하면 그 자리에서 핸들러가 실행됩니다.

✕ 응답을 놓칠 수 있는 코드
@Override protected EventStepResult onEnter(EventStepContext ctx) {
    ctx.eventBus().publish(new LlmRequested("hi"));    // ① 여기서 응답이 즉시 발행되면?
    return EventStepResult.await(                       // ② 구독은 이 결과가 처리된 뒤에 등록됨
            AwaitCondition.event(LlmResponded.class));  // → 응답을 영원히 못 받는다
}

요청을 받은 쪽이 캐시 히트나 동기 처리로 즉시 응답을 발행하면, 그 시점에는 아직 구독이 없습니다. 응답은 사라지고 Flow는 마감까지 멍하니 기다립니다. 재현이 어렵고 운영에서만 가끔 터지는 버그입니다.

✓ 효과로 넘기면 순서가 뒤집힌다
return EventStepResult
        .await(AwaitCondition.event(LlmResponded.class))   // ① 먼저 구독 등록
        .thenPublish(new LlmRequested("hi"));              // ② 그 다음 발행 — 안전
체이닝실행 스레드쓸 곳
thenPublish(event)루프 스레드이벤트 발행. 가장 흔한 형태.
thenRun(effect)루프 스레드카운터 증가, 로그 등 즉시 끝나는 동작.
thenRunAsync(effect)비동기 실행기HTTP·DB·LLM 호출처럼 블로킹될 수 있는 동작.

블로킹 작업 다루기

비동기 실행기 등록 + 사용
ExecutorService pool = Executors.newFixedThreadPool(8);

EventWorker worker = EventWorker.builder("agent")
        .clock(SystemClock.INSTANCE)
        .eventBus(bus)
        .asyncExecutor(pool)          // ← 없으면 runAsync가 예외
        .build();

// Step 안
@Override protected EventStepResult onEnter(EventStepContext ctx) {
    final String callId = ctx.flowId().flowKey();     // ① 불변 값을 미리 캡처
    return EventStepResult
            .await(AwaitCondition.signal("llm", callId),
                   AwaitCondition.signal("llm-error", callId),
                   AwaitCondition.deadlineIn(60_000))
            .thenRunAsync(c -> {                       // ② 여기부터는 다른 스레드
                try {
                    c.signal("llm", callId, llmClient.complete(prompt));
                } catch (Exception e) {

                }
            });
}
비동기 작업의 예외는 Flow를 실패시키지 않습니다

runAsync로 넘긴 작업이 예외를 던지면 Flow는 아무것도 모른 채 계속 기다립니다. 결국 마감이 올 때까지 멈춰 있게 됩니다. 그래서 위 예제처럼 실패도 반드시 신호로 알려야 하고, 그 신호도 await에 선언해 두어야 합니다.

비동기 작업 안에서 흐름 상태를 읽지 마세요

비동기 작업은 루프 스레드 밖에서 돕니다. 그 시점에 Flow는 이미 다른 Step으로 넘어갔을 수 있습니다. ctx.currentStepId() 같은 가변 상태를 읽지 말고, 필요한 값은 결과를 반환하기 전에 지역 변수로 캡처하세요.

효과는 exactly-once가 아닙니다

durable Flow에서 프로세스가 특정 시점에 죽으면 두 가지 문제가 각각 생길 수 있습니다. 대기는 저장됐는데 요청은 나가지 않은 상태로 복구되거나, 반대로 같은 효과가 두 번 실행될 수 있습니다.

중요한 외부 작업(결제, 메일 발송, 도구 실행)에는 durable outbox나 안정적인 연산 ID(idempotency key)를 반드시 함께 쓰세요. 프레임워크가 대신해 줄 수 없는 부분입니다.

08EventSignal

클래스 하나뿐이지만 durable 흐름의 핵심입니다.

EventSignal은 (이름, 키, 선택적 페이로드)로 이루어진 이벤트입니다. ctx.signal("tool-call", callId, result)로 발행하고, AwaitCondition.signal("tool-call", callId)로 기다립니다.

왜 따로 있나

“내 주문의 응답만 받고 싶다”를 표현하는 방법은 두 가지입니다 — predicate(람다)를 쓰거나 데이터 모양의 키를 쓰는 것. 람다는 체크포인트에 저장할 수 없습니다. 그래서 (이름, 키)라는 저장 가능한 상관 방식이 따로 마련되어 있습니다. durable 흐름에서 특정 대상을 기다릴 때는 시그널을 쓰세요.

API비고
EventSignal.of(name, key)페이로드 없는 신호
EventSignal.of(name, key, payload)페이로드 null이면 예외
ctx.signal(name, key[, payload])Step 안에서 발행하는 단축 메서드
worker.signal(name, key[, payload])바깥(웹훅 컨트롤러 등)에서 발행
sig.payload(Type.class)타입 캐스팅. 페이로드가 없으면 null
헷갈리는 지점 · Core의 “시그널”과 이름만 같습니다

이렇게 보입니다 Core에서 ctx.signal("paid")를 썼으니 여기서도 Step 로컬 메모로 쓰면 되겠다.

실제로는 완전히 다른 물건입니다.

· Core의 시그널: Step 안의 메모. 밖으로 나가지 않고 그 Step이 끝나면 사라집니다.
· EventLoop의 시그널: EventBus에 발행되는 이벤트. 같은 버스를 공유하는 모두가 볼 수 있고, await로 명시적으로 기다려야 전달됩니다.

즉 여기서 ctx.signal(...)은 “메모를 남긴다”가 아니라 “방송한다”입니다. 기다리는 await가 없으면 그냥 사라집니다.

09Durable — 제약과 복구

Core의 durable에 “무엇을 기다리고 있었는지”가 추가로 저장됩니다.

저장되는 것
  • 현재 Step과 진입 여부
  • 대기 조건 목록(이벤트 타입 이름 · 시그널 이름/키 · 마감 시각)
  • 실행 신원(runId, traceId 등)
저장되지 않는 것
  • Step 인스턴스의 필드
  • predicate 람다
  • 주고받은 이벤트 객체
  • 효과의 실행 여부
마감은 절대 시각으로

“30초 후”가 아니라 “몇 시 몇 분”으로 저장됩니다. 재시작할 때마다 마감이 뒤로 밀리지 않습니다.

durable 모드의 제약

제약언제 터지나대응
predicate 있는 이벤트 대기 금지대기를 걸 때(런타임)signal(name, key)로 바꾸거나, 전부 받고 onEvent에서 걸러 null을 반환
onRecover 구현 필수복구할 때(런타임)기본 구현이 실패입니다. durable Step은 반드시 재정의하세요.
durable 저장소 필수submit()빌드는 통과합니다. 통합 테스트에서 제출까지 해 봐야 잡힙니다.
헷갈리는 지점 · predicate 금지는 “그 Step이 실행될 때” 터집니다

이렇게 보입니다 durable Flow에 predicate를 쓰면 빌드에서 막아 주겠지.

실제로는 AwaitCondition.event(Foo.class, predicate) 자체는 문제없이 만들어집니다. 문제는 워커가 그 대기를 체크포인트로 저장하려는 순간 드러납니다 — 즉 그 Step이 실제로 실행될 때입니다.

흐름의 5번째 Step에서만 predicate를 썼다면 앞의 4단계는 정상 동작하다가 운영 중 그 지점에서야 실패합니다. durable로 전환할 때는 모든 Step의 await를 한 번씩 훑어보세요.

// ✕ durable에서 실패
AwaitCondition.event(ToolDone.class, e -> e.callId().equals(myCallId))

// ✓ 데이터로 상관관계를 표현 — 저장 가능
AwaitCondition.signal("tool-done", myCallId)

// ✓ 또는 전부 받고 onEvent에서 거른다
AwaitCondition.event(ToolDone.class)
// onEvent: if (!e.callId().equals(myCallId)) return null;

onRecover 작성법

저장된 대기를 되살리는 표준형
@Override
protected EventStepResult onRecover(EventStepContext ctx, EventRecoveryContext recovery) {
    List<AwaitCondition> conditions = new ArrayList<>();

    for (EventAwaitCheckpoint saved : recovery.awaits()) {
        switch (saved.type()) {
            case SIGNAL:
                conditions.add(AwaitCondition.signal(saved.signalName(), saved.signalKey()));
                break;
            case DEADLINE:
                // 절대 시각 → 지금 기준 남은 시간 (이미 지났으면 0)
                conditions.add(AwaitCondition.deadlineIn(recovery.millisUntil(saved, ctx.now())));
                break;
            case EVENT:
                conditions.add(AwaitCondition.event(ToolDone.class));
                break;
        }
    }
    // ★ 여기서 요청을 다시 보내면 안 된다 — 이미 보냈다
    return EventStepResult.await(conditions.toArray(new AwaitCondition[0]));
}
시작 시 복구
EventFlowFactoryRegistry registry = EventFlowFactoryRegistry.builder()
        .register("llm-call", id -> buildFlow(id.flowKey()))
        .build();

EventFlowRecoveryService recovery =
        EventFlowRecoveryService.create(store, registry);

worker.start();
int restored = recovery.recoverActiveForWorker(worker);
헷갈리는 지점 · 복구는 “이어서 실행”이 아니라 “다시 기다리기”입니다

이렇게 보입니다 복구하면 Flow가 알아서 원래 하던 대로 이어서 진행되겠지.

실제로는 복구가 되살리는 것은 “어느 Step에서 무엇을 기다리고 있었다”는 사실뿐입니다. 실제로 대기를 다시 거는 것은 onRecover가 반환하는 await(...)입니다. 즉 Step이 협조하지 않으면 복구가 완성되지 않습니다.

· onRecover 미구현 → 복구 즉시 실패
· 대기를 적게 선언 → 저장돼 있던 조건 일부가 영영 되살아나지 않음
· onEnter를 그대로 호출 → 요청이 두 번 나감

이 “불편함”은 의도된 것입니다. 무엇을 다시 하고 무엇을 하지 말아야 하는지는 도메인만 알 수 있기 때문입니다.

여러 프로세스에서 복구할 때

중복 실행 방지는 전적으로 애플리케이션 책임입니다. 리더 선출 · DB 행 잠금 · 리스 중 하나를 적용하세요. findActiveByWorker(name)로 인스턴스별 워커 이름을 나누는 것이 가장 현실적인 완화책입니다.

리스너 인터페이스는 Core와 완전히 동일합니다. 트레이스에는 두 이벤트가 추가됩니다.

리스너 등록
EventWorker worker = EventWorker.builder("agent")
        .clock(SystemClock.INSTANCE)
        .eventBus(bus)
        .listener(myListener)        // Engine이 아니라 워커에 직접
        .build();

onFlowSubmitted · onStepEntered · onStepExited · onFlowFinished · onFlowFailed · onFlowCancelled — Core와 같은 콜백입니다. 같은 리스너 객체를 Core Worker와 EventWorker에 함께 등록해도 됩니다.

대기·재개 이벤트

트레이스 리스너를 붙이면 이 런타임에만 있는 두 이벤트가 나옵니다.

이벤트내용
FLOW_WAITING대기 등록 직후. 무엇을 기다리는지(조건 목록)를 담습니다.
FLOW_RESUMED깨어날 때. 왜 깨어났는지(EVENT/SIGNAL/TIMEOUT/RECOVERY)를 담습니다.
실제 대기 시간을 그대로 측정할 수 있습니다

짝을 이루는 FLOW_WAITING과 FLOW_RESUMED의 시각 차이가 실제 대기 시간이고, 재개 사유가 그 대기가 어떻게 끝났는지(응답/타임아웃)를 알려 줍니다. LLM 응답 지연 분포나 승인 소요 시간을 바로 얻을 수 있습니다.

헷갈리는 지점 · stateOf()가 null이면 “실패”가 아닙니다

이렇게 보입니다 worker.stateOf(id)가 null이면 뭔가 잘못된 것이다.

실제로는 “활성 목록에 없다”는 뜻일 뿐입니다. 정상 완료해서 제거된 경우가 가장 흔합니다. 아직 제출한 적 없어도 null입니다.

최종 결과를 알고 싶으면 Flow 객체의 state()를 읽거나 종료 리스너를 쓰세요.

11테스트

Core만큼 결정적으로 테스트할 수 있습니다. tickOnce() 자리에 drain()이 들어갑니다.

기본 패턴
@Test
void 응답이_오면_완료된다() {
    ManualClock clock = new ManualClock();
    InMemoryEventBus bus = InMemoryEventBus.create();
    EventWorker worker = EventWorker.builder("llm")
            .clock(clock).eventBus(bus).build();     // start() 호출 안 함!

    EventFlow flow = buildFlow();
    worker.submit(flow);
    worker.drain();                                   // 진입 + 대기 등록까지 전부 처리

    assertThat(flow.state()).isEqualTo(FlowState.RUNNING);   // 대기 중

    bus.publish(new LlmResponded("hi"));              // 동기 발행
    worker.drain();                                   // 그 처리까지

    assertThat(flow.state()).isEqualTo(FlowState.FINISHED);
}

@Test
void 마감이_지나면_대체경로로_간다() {
    // … 동일한 준비 …
    worker.submit(flow);
    worker.drain();

    clock.advance(30_000);                            // 시간을 즉시 통과
    worker.drain();                                   // 만료된 마감 처리

    assertThat(log).containsExactly("fallback");
}
헷갈리는 지점 · drain()과 start()는 섞을 수 없습니다

이렇게 보입니다 start()로 띄워 두고 테스트에서 drain()으로 한 번 더 밀어주면 확실하겠다.

실제로는 drain()은 백그라운드 모드면 즉시 예외를 던집니다. 테스트에서는 start()를 아예 호출하지 않고 ManualClock + drain()만 쓰세요.

체크리스트
  • drain()은 더 이상 진행할 것이 없을 때까지 반복합니다. 대기 없이 이어지는 Step 10개도 한 번에 통과합니다.
  • 시간은 전부 ManualClock.advance()로.
  • 이벤트는 bus.publish(...)로 테스트 스레드에서 직접 발행.
  • runAsync를 쓰는 Step은 같은 스레드에서 실행하는 Executor(Runnable::run)를 주면 결정적으로 검증할 수 있습니다.

중요한 외부 작업을 효과에만 의존outbox 또는 idempotency key 병행 — exactly-once가 아닙니다
이 런타임의 가장 흔한 장애는 “실패”가 아니라 “영원한 대기”입니다

마감 없는 await, 예외로 죽은 비동기 작업, 조용히 무시된 깨우기 — 전부 로그에 아무것도 남지 않은 채 멈춘 Flow를 만듭니다.

대비책은 하나뿐입니다 — 모든 await에 마감을 함께 거세요. 마감이 있으면 최소한 onTimeout이 호출되어 문제가 드러납니다.

한 줄 원칙

“Step은 무엇을 기다릴지 선언하고, 깨어나면 판단만 한다.” 기다림을 선언하지 않은 것은 절대 오지 않습니다.

기억해야 할 8가지

  1. 대기 중인 Flow는 코드가 한 줄도 실행되지 않는다. 깨워줄 사람이 없으면 영원히 잔다.
  2. await는 추가가 아니라 통째로 교체다.
  3. 마감을 여러 개 걸면 가장 이른 것 하나만 산다.
  4. onTimeout과 onRecover의 기본 동작은 실패다.
  5. null 반환의 의미는 훅마다 다르다.
  6. 요청은 thenPublish로 — 구독이 먼저, 발행이 나중.
  7. 비동기 작업의 예외는 Flow에 전달되지 않는다. 실패도 신호로.
  8. durable이면 predicate 금지, onRecover 필수.
